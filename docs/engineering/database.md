# Database and Supabase standards

> Source: distilled from the approved implementation plan and AI harness design (30 Oct 2026). References such as `plan 07 §4.2`, `03` §10 or `ADR-009` point to the archived plan, the harness design documents, or `docs/adr/`. From Stage 1 (S1-T12) this repository is authoritative (HD-11).

Scope: migrations, Row Level Security, grants, functions, storage policies, types, seeds. Daily work uses the hosted `findsprop-dev` project; a local Docker stack is optional and CI runs the database checks (ADR-034).

## Data-access architecture

| Concern                    | Rule                                                                                                                                                                                                                                                                  |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reads                      | `features/*/queries.ts`, `server-only`; explicit columns; map rows → view models; choose client: `publicAnon` (cacheable public), `server` (user JWT, RLS)                                                                                                            |
| Writes                     | `features/*/service.ts` called by Server Actions; prefer RPC for multi-statement or rule-bearing writes; user-scoped client by default                                                                                                                                |
| Service role               | Only in allow-listed modules (`builders`, `forms`, `crm`, `media`, `server/rate-limit`, selected route handlers) for operations that RLS deliberately denies the user: lead/event inserts for anonymous visitors, CRM secrets, Auth admin API, Storage finalize/sweep |
| Business rules             | Enforced twice: service/RPC (nice errors) **and** triggers/RLS (cannot be bypassed)                                                                                                                                                                                   |
| Validation                 | Zod at the edge (shape, ranges, normalisation); DB constraints for invariants; dynamic forms validated against stored field definitions server-side (BR-60)                                                                                                           |
| Error normalisation        | `normalise-error.ts` maps Postgres/PostgREST/Storage/Auth errors to the closed `ErrorCode` set; custom `RAISE EXCEPTION … USING ERRCODE` values for rule violations (for example `P0001` family with stable message keys)                                             |
| Audit                      | Triggers for state changes; `audit()` helper for service-level events                                                                                                                                                                                                 |
| External calls             | Adapters with timeouts (default 5 s SMS/places, 10 s CRM), bounded retries for idempotent calls only, circuit-breaker-free (volumes are low), full redaction in logs                                                                                                  |
| Browser access to Supabase | Only Storage uploads to a signed URL and the Auth client methods required by flows (OTP verify, MFA challenge). **No browser-side table access**; the publishable key is therefore low-risk but RLS is still complete                                                 |

## Transactions and atomic workflows

Multi-step writes that must succeed or fail together are Postgres functions called through RPC (one round trip, one transaction). Each has pgTAP coverage.

| Workflow             | Function                                           | Contents                                                                                                                                                                                                                                                                           |
| -------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Submit listing       | `submit_listing(listing_id)`                       | owner check, completeness (≥1 photo, address, location), pending cap, status → `pending`, `submitted_at`, audit                                                                                                                                                                    |
| Finalize photo       | `finalize_listing_media(listing_id, path, …)`      | lock listing row, enforce ≤6, set cover if first, insert row                                                                                                                                                                                                                       |
| Owner status         | `set_listing_status(listing_id, 'sold'\|'rented')` | only from `approved`; audit                                                                                                                                                                                                                                                        |
| Moderate listing     | `moderate_listing(listing_id, action, reason?)`    | admin only; reject needs reason; audit; returns updated row                                                                                                                                                                                                                        |
| Send enquiry         | `submit_enquiry(...)`                              | rate limit + 24 h de-dupe + insert (SECURITY DEFINER; checks `auth.uid()`)                                                                                                                                                                                                         |
| Project lead         | `submit_project_lead(...)`                         | rate limit + insert (+ event)                                                                                                                                                                                                                                                      |
| Form submission      | `record_form_submission(...)`                      | rate limit, insert submission, mirror `project_leads` when name+phone present (BR-63), return ids; field validation against stored definition happens in the action before the call (BR-60)                                                                                        |
| Track event          | `track_project_event(...)`                         | rate limit 30/min, view de-dupe per project per hour                                                                                                                                                                                                                               |
| Rate limit           | `rate_limit_hit(...)`                              | atomic upsert                                                                                                                                                                                                                                                                      |
| Arm/disarm CRM retry | `arm_crm_retry()` / `disarm_crm_retry()`           | reads URL from `app_config`, token from `internal_cron_tokens`                                                                                                                                                                                                                     |
| Invite builder       | _application-level saga_                           | (1) create Auth user with **confirmed** email via admin API; (2) DB transaction: insert `user_roles` + `builders`; (3) send set-password email. If (2) fails, delete the Auth user (compensation); if (3) fails, builder row stays and "Resend invitation" works (BR-15, ANA A-05) |

Cross-system operations (Auth, Storage, email, CRM HTTP) are **not** transactional: each is written as idempotent steps with explicit compensation, and failures are logged with the request id (`09` §6).

## Migrations, local development, seeds and rollback

### 10.1 How the schema is derived, and the order it is built

**Derivation (no demo SQL).** `S3-T01` produces a rule-to-schema checklist from `06-business-rules-and-data.md` and `07-supabase-interactions.md`, settles column lists from the page and form specifications (ANA `04`, UX post-property, project form, lead forms, CMS editors), and records ambiguities as questions for you instead of inferring them from the demo's code. Every database-enforced rule is then written as a trigger, policy, constraint or function with a named pgTAP test (`08` §10).

| Rule                                     | Enforced by (new schema)                                                   |
| ---------------------------------------- | -------------------------------------------------------------------------- |
| BR-02/03 profile + default role          | `handle_new_user()` trigger on `auth.users` (null-email safe)              |
| BR-11/12/13 reserved super admin         | role-grant trigger + `user_roles` guard + RLS excluding `super_admin` rows |
| BR-20…25 listing moderation              | `properties` guard trigger + RLS + column grants                           |
| BR-26 owner-scoped delete                | RLS                                                                        |
| BR-27/28 listing and property types      | CHECK constraints                                                          |
| BR-30…35 builder isolation and guards    | `current_builder_id()`, `project_is_mine()`, builder guard trigger, RLS    |
| BR-40…43 project moderation, re-approval | `projects` guard trigger + `project_is_live()` + RLS                       |
| BR-44 delete blocked with leads          | `project_leads.project_id ON DELETE RESTRICT`                              |
| BR-45…47 unit and lead locks             | guard triggers                                                             |
| BR-50…53 enquiries and saved homes       | RLS, RPC `submit_enquiry`, unique `(user_id, property_id)`                 |
| BR-60…67 forms and CRM                   | tables + service-only secrets + retry functions reading `app_config`       |
| BR-70…75 rate limits and visitor hash    | `rate_limit_hit()` + service-side HMAC                                     |
| BR-80/81 CMS defaults                    | `site_settings` + app-side merge                                           |

Rules: one concern per migration; idempotent guards (`if not exists`) only where safe; no data loss without an explicit expand/contract plan; no `DROP` in the same migration that introduces its replacement for live data; CI applies the whole chain to an empty database and runs pgTAP.

### 10.2 Local development and seed data

- The hosted `findsprop-dev` project provides Postgres, Auth, Storage and Studio; its auth settings (test phone numbers with fixed OTPs, so no SMS is sent) are set in the dashboard. With Docker, `supabase start` gives the same locally plus Inbucket for email; CI always uses a throwaway stack.
- `supabase/seed.sql`: fictional Tamil Nadu content (≈60 listings across several cities with coordinates, 6 builders, 12 projects with units and trends, a default contact form, `site_settings` defaults with sample sponsors). All people, prices and phone numbers fictional.
- `scripts/seed-dev.mjs`: creates test users through the Auth admin API (customer, owner, active builder, inactive builder, super admin using the reserved email in **local only**), uploads sample images to local Storage, attaches `listing_media`. **Refuses to run** unless the Supabase URL is local or on an explicit dev allow-list.
- Production never receives seed data.

### 10.3 Staging and production separation

Separate projects, keys, buckets, users, redirect URLs and secrets. GitHub Environments `dev` and `production` hold the project ref, DB password and access token; `production` requires a reviewer. Vercel Preview → dev keys; Vercel Production → prod keys; no prod secret is available to Preview (`09` §2).

### 10.4 Rollback and recovery

- Forward-only. Each migration PR includes a **rollback note**; destructive or behaviour-changing migrations also include a reviewed `supabase/rollbacks/<timestamp>.sql` that is _not_ auto-run.
- Use expand → migrate → contract for breaking changes across two releases.
- Before any production migration: confirm last backup, take a logical dump of affected tables if data changes, run the same migration on a prod-shaped copy (staging or restored snapshot).
- Failure handling: migrations are transactional; non-transactional statements (for example concurrent index builds) live in their own file; a failed deploy stops the pipeline and the release is **not** promoted.
- Recovery: Supabase daily backups (Pro, 7 days); PITR if `DEC-30` approves; restore drill before launch (`09` §7).

## RLS plan per table

Policies target `anon` or `authenticated` explicitly. Use `(select auth.uid())` and `(select has_role(...))` forms so Postgres evaluates them once per statement. `has_role`, `is_super_admin`, `current_builder_id`, `project_is_live`, `project_is_mine` are `SECURITY DEFINER` with pinned `search_path`, `EXECUTE` revoked from `public` and granted only to `anon`/`authenticated` as needed. Views, if any, use `security_invoker = true`.

Legend: **S** select, **I** insert, **U** update, **D** delete; "own" = row tied to the caller; "—" = no access.
