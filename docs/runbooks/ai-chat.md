# AI chat: run it, watch it, switch it off, roll it out

How to operate the AI chat assistant of findsprop (ADR-128): the variables, the kill switch, the usage rows, the daily budget, switching provider, incidents, rollback, and the staged rollout the **owner** runs. The design and the reasons are in `docs/adr/128-ai-chat-assistant.md`; the build plan is `docs/ai-chat-phase-plan.md`.

**State when this page was written (15 Nov 2026).** The chat is built up to AI-P6-T01 and merged on `develop`. It is switched off everywhere (`FLAG_AI_SEARCH` is off by default). Nothing here was run against dev, staging or production: every command and screen below was read from the repository, not tried. Where something could not be checked from the repository it says **not verified**. Staging and production environments are not known to exist yet (`docs/status.md` says the sign-in guard is to be switched on there "when those projects exist"), so those checks are written for when they do.

**Who does what.** The _owner_ is the only person who changes Vercel variables, Supabase projects, provider keys and the flag. An _agent session_ reads the repository, writes fixes as pull requests, and never touches dev, staging or production, never reads a key and never switches the flag. Nobody pastes a key or a customer's words into chat.

**The confirm card (AI-P6-T02, PR 227) is merged, and this page was updated for it afterwards.** The two propose tools `propose_enquiry` and `propose_site_visit` (`src/features/ai-chat/tools/registry.ts`) sign a proposal (valid for 30 minutes, `PROPOSAL_LIFETIME_SECONDS` in `src/config/ai.ts`, tied to the signed-in customer, with a message of at most 1,000 characters). After the checked answer the endpoint streams a **confirm card** built on the server (`src/features/ai-chat/confirm/build-card.ts`): the target, the message and, for a visit, the day come from the signed proposal; the customer's name and verified phone come from their account. Nothing is sent until the customer presses **Send** on the card. The click runs `confirmChatProposal` (`src/features/ai-chat/actions.ts`), which checks the proposal again and then runs the existing `sendEnquiry` or `submitProjectLead` as that customer (`src/features/ai-chat/confirm/send.ts`). All of this was read from the code and its tests; none of it was tried in dev, staging or production (checks D13 to D15 in section 9.1 do that). The e2e test for the card runs only with the flag on and had not been run when the ledger recorded the merge.

A malformed value stops the build or the boot with a message that lists the variable **names** only. Never type a value into chat, a file in the repository or a pull request.

## 3. The kill switch

**What it does.** With `FLAG_AI_SEARCH` off: `/ai-search` is a 404 page; `POST /api/ai/chat` answers 404 with no body and does nothing else (no parsing, no limit spent, no provider call, no usage row); the header, footer and search-card links to the chat are not drawn. A visitor who still has the chat open and presses Send gets the generic "We couldn't answer that" notice, because the 404 has no body to read (`src/features/ai-chat/chat/chat-stream.ts`). Nothing is lost: the transcript stays in that tab only.

**How to switch it off fast (owner).**

1. Vercel, the project, **Settings, Environment Variables**: set `FLAG_AI_SEARCH` to `0` for the environment (or delete it) and save.
2. **Redeploy** that environment (Deployments, the latest one, Redeploy). The change reaches only a new deployment, so the chat stays on until the new one is live. How long that takes is **not verified**: time it in the dev drill (section 9, check D12) and write the number here.
3. Confirm: the command in section 9, check D1, give `404`.

The Vercel screen names above are from memory of the product and **not verified** against the current dashboard. Whether Vercel's instant rollback to an older deployment also restores that deployment's older variable values is **not verified**; do not rely on it for the switch until the drill shows it.

**What is not switched off.** The read-only Server Action behind the answer cards (`readChatCardsAction`, ADR-125) does not look at the flag; it returns at most three public cards for ids it is given and is reachable only from the chat island. With the flag off nothing calls it. **The confirm card's Send action does not honour the flag either.** `confirmChatProposal` needs a signed-in customer with a verified phone and checks the signed proposal, but nothing in its configuration (`src/features/ai-chat/action-config.ts`) reads `FLAG_AI_SEARCH`. So with the flag off, a card that is already on a customer's screen can still be sent until its proposal expires (up to 30 minutes after it was made), by the code alone. **Not verified:** whether a tab opened before a redeploy still reaches the send once the new build is live (the new build has its own action ids, and whether the hosting keeps the old ones working is not shown by the code); check D15 records what really happens. The same redeploy applies to the secret change below. No new card can appear, because the endpoint answers 404. If a send must stop at once, the only lever found in the code is changing `RATE_LIMIT_HMAC_SECRET`: every open proposal then fails its signature check, the send answers `NOT_FOUND` and the card shows "This request is no longer valid" (`verifyProposal` in `src/features/ai-chat/tools/proposal.ts`; not tried). It also changes every visitor's hashes (section 7.3, step 5), so use it only when waiting out 30 minutes is not acceptable.

## 4. Reading the usage rows

**Where.** One row per customer message in `public.ai_usage_events`. It has row-level security on, no policy and no grant for `anon` or `authenticated`: not even the admin pages can read it. Read it in the Supabase **SQL Editor** of the environment (as the retention runbook does). Never select anything you do not need.

**What is in it, and what is not.** The time, `request_id` (the same id as the `x-request-id` response header and the `requestId` on the log lines), `caller` (`anonymous` or `signed_in`), `user_id` (signed in only) or `visitor_hash` (anonymous only, an HMAC, never the address), `provider`, `model`, `prompt_version`, `outcome`, `limited_by`, the rule names in `input_tags` and `output_tags` with `output_counts`, `number_ungrounded`, `rounds`, `retried`, `tool_calls_per_round`, `tools_ran`, the three token counts, `agent_limit`, `fallback_reason` and `duration_ms`. **There is no column for message text, a phone, an email, a name or a search word, and none is stored**; checks in the table refuse anything but snake_case words in the tag and tool lists. So a row can say that something was blocked and by which rule, never what was said. Treat `user_id` and `visitor_hash` as personal data: do not paste them anywhere, and leave them out of queries unless you are chasing abuse.

**Values.** `outcome` is one of `answered`, `limit` (a round or tool cap forced a short answer), `refused` (the input check), `blocked` (the output check stopped the answer), `fallback` (no usable answer), `aborted`, `error`, `rate_limited`. `limited_by` is one of the five limit names (section 5). `agent_limit` is `round_cap`, `tool_cap` or `time_limit`; `fallback_reason` is `provider_error`, `refused`, `empty_answer` or `time_limit`. Input rule tags: `competitor`, `injection_suspected`, `injection_doubtful`, `internals_probe`, `personal_data`, `flooding`, `check_failed`. Output rule tags: `prompt_leak`, `internals_leak`, `competitor`, `contact_blocked`, `unknown_reference`, `advice_phrase`, `format_stripped`, `check_failed`. `number_ungrounded` is the shadow-mode count of figures the number check could not match to a tool result (it only counts; it blocks nothing).

**Retention.** The nightly job deletes rows older than 12 months (provisional, owner to confirm: `docs/runbooks/retention.md`). Deleting a user account sets `user_id` to null; the row stays as an anonymous fact.

**Safe queries** (read-only; days are India dates, midnight to midnight, whereas the daily limits and the budget count from 05:30 India time, section 5):

```sql
-- Messages per day and outcome, last 14 days
select (occurred_at at time zone 'Asia/Kolkata')::date as day, outcome, count(*) as messages
from public.ai_usage_events
where occurred_at >= now() - interval '14 days'
group by 1, 2
order by 1 desc, 2;
```

```sql
-- Which limit refused, per day
select (occurred_at at time zone 'Asia/Kolkata')::date as day, limited_by, count(*) as refused
from public.ai_usage_events
where outcome = 'rate_limited' and occurred_at >= now() - interval '14 days'
group by 1, 2
order by 1 desc, 3 desc;
```

```sql
-- Anonymous against signed-in, per day
select (occurred_at at time zone 'Asia/Kolkata')::date as day, caller, count(*) as messages
from public.ai_usage_events
where occurred_at >= now() - interval '14 days'
group by 1, 2
order by 1 desc, 2;
```

```sql
-- Tokens per day and model (messages that reached the model)
select (occurred_at at time zone 'Asia/Kolkata')::date as day, provider, model,
       count(*) as messages, sum(input_tokens) as input_tokens,
       sum(cached_input_tokens) as cached_input_tokens, sum(output_tokens) as output_tokens
from public.ai_usage_events
where input_tokens > 0 or output_tokens > 0
group by 1, 2, 3
order by 1 desc, 4 desc;
```

```sql
-- Cost estimate by model. THE PRICES ARE NOT IN THE REPOSITORY: put the provider's current prices
-- (USD per million tokens) in the three <...> places, from its price page, and note the date you read them.
-- OpenAI counts cached tokens inside the input tokens (the spike script takes them out of the input the same way:
-- scripts/ai-spike/run.mts), so they are taken out of the input here. Rows with no tokens (refused, rate limited) add 0.
-- For another provider check that before trusting the figure. This is an estimate, never an invoice.
with price(model, usd_input, usd_cached, usd_output) as (
  values ('<model id>', <price input>::numeric, <price cached input>::numeric, <price output>::numeric)
)
select (event.occurred_at at time zone 'Asia/Kolkata')::date as day, event.model,
       count(*) as messages,
       round(sum(
         ((event.input_tokens - event.cached_input_tokens) * price.usd_input
          + event.cached_input_tokens * price.usd_cached
          + event.output_tokens * price.usd_output) / 1000000.0
       ), 4) as estimated_usd
from public.ai_usage_events as event
join price on price.model = event.model
group by 1, 2
order by 1 desc;
```

```sql
-- Rule tags that fired (input rules, and output rules whether they block or only change the text), last 7 days
select tag, count(*) as messages
from public.ai_usage_events, unnest(input_tags || output_tags) as tag
where occurred_at >= now() - interval '7 days'
group by tag
order by messages desc;
```

```sql
-- How often each output rule fired (a count of firings, not of messages)
select rule, sum(value::int) as times
from public.ai_usage_events, jsonb_each_text(output_counts) as counts(rule, value)
where occurred_at >= now() - interval '7 days'
group by rule
order by times desc;
```

```sql
-- Caps and fallbacks: how often a limit forced a short answer, and why no answer was made
select agent_limit, fallback_reason, count(*) as messages
from public.ai_usage_events
where (agent_limit is not null or fallback_reason is not null) and occurred_at >= now() - interval '7 days'
group by 1, 2
order by 3 desc;
```

```sql
-- Speed: median and 95th percentile of a message, in seconds, for answered messages
select percentile_cont(0.5) within group (order by duration_ms) / 1000.0 as median_s,
       percentile_cont(0.95) within group (order by duration_ms) / 1000.0 as p95_s,
       avg(rounds) as mean_rounds
from public.ai_usage_events
where outcome in ('answered', 'limit') and occurred_at >= now() - interval '7 days';
```

```sql
-- Abuse: callers with the most messages in the last day (the hash is cut to 8 characters; no user ids)
select caller, left(visitor_hash, 8) as visitor, count(*) as messages
from public.ai_usage_events
where occurred_at >= now() - interval '1 day' and caller = 'anonymous'
group by 1, 2
order by 3 desc
limit 10;
```

## 5. The daily budget and the alert

**What the budget is.** A count of **messages**, not money: `AI_GLOBAL_DAILY_MESSAGE_BUDGET` in `src/config/ai.ts`, **390** (set 16 Nov 2026 from the measured cost below, for the owner's target of $1 a day for the whole app). Every caller together shares it. It is spent only by a message that passed every earlier limit; a message refused by the input check never spends it.

**Measured cost and time per message (AI-P8-T03, 16 Nov 2026, dev site, `gpt-6-luna`, provider `openai`).** Sample: 20 real messages sent to the dev address with `curl` (no cookie, so each was its own anonymous caller): 8 searches (English 4, Tamil 2, Tanglish 2), 2 compares (English, Tanglish), 2 builder questions (English, Tanglish), 3 EMI sums (English, Tamil, Tanglish), 2 messages the input check refused (a prompt-injection try, a rival portal), 1 investment question the model declined, 1 "I do not know", and 1 project question in Tamil. Customer words were made-up questions, no personal data. Token counts and times are the `ai_usage_events` rows the app wrote (`input_tokens`, `output_tokens`, `duration_ms`); nothing was estimated. Price used, as given by the owner and **not checked against the provider's page**: $0.10 per 1M input tokens and $0.50 per 1M output tokens. Every input token was priced at that full rate even though 90 to 99% of them were served from the provider's cache (cheaper), so the figures are an upper bound. Total spent by the measuring run: about **$0.03**, far under the $2 cap.

| Measure                                | Cost per message                                                                                         | Time per message          |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------- |
| Median (all 20)                        | $0.00164                                                                                                 | 6.7 s                     |
| 90th percentile (nearest rank)         | $0.00243                                                                                                 | 10.4 s                    |
| Most expensive / slowest               | $0.00253 (request 6cea09f8, a Tanglish builder question that hit the five-round cap: 23,162 in, 431 out) | 12.4 s (the same request) |
| Mean                                   | $0.00147                                                                                                 | n/a                       |
| Median of the 18 that called the model | $0.00165                                                                                                 | n/a                       |

Shapes seen: a greeting or "I do not know" is one round (about 5,000 in); an EMI sum is two rounds (about 10,300 in, 110 to 135 out); a search is two to four rounds (10,000 to 21,000 in); a compare is three or four rounds (16,000 to 21,000 in); the two builder questions and one Tamil project question ran into the five-round cap (outcome `limit`, 22,700 to 23,400 in), which is the dearest shape. The two input-check refusals cost nothing (no model call). Limits of the sample: 20 messages, one conversation turn each (no long histories), dev data (few listings), so a real day with long conversations and more listings will cost more per message; measure again from the real usage rows after the first week (query below) and after any change of model, prompt or tools.

**How the 390 was derived.** $1 divided by the dearest message measured ($0.00253) is 395; the budget is 390, so the day stays under $1 **even if every message costs as much as the dearest one measured**. At the 90th percentile ($0.00243) $1 would allow 410, at the median 610. This holds **for the measured shapes** (single-turn questions, dev data, at most 23,200 input tokens). The five-round and six-tool-call caps bound the rounds, but there is no total cap on history length yet (open item L1 in the ledger), so a long conversation can cost more per message than any of the 20. With that caveat a message count is a good enough guard today. A dollar-based check (summing token cost from the usage rows and stopping at $1) is **not built**: it would need a new counter or a migration, and the count already bounds the spend while the per-message cost stays within what was measured. Build one if the model or its price changes, if histories get longer, or if the owner wants the stop to follow real money; until then watch the usage rows weekly.

**The five limits** (numbers in `src/config/ai.ts`): free trial 2 messages over 366 days per browser (`ai_chat_trial`); anonymous address backstop 40 a day (`ai_chat_trial_ip`); burst 10 a minute (`ai_chat_burst`); signed in 40 a day (`ai_chat_user_day`); the global budget (`ai_chat_global_day`). Windows are fixed, counted from the start of the clock period in **UTC**: the daily ones reset at **05:30 India time**, not at midnight. The windows are aligned to the clock, not to each caller's first message, so the 366-day trial resets for **everyone at the same moment** (next: 13 Feb 2027, 05:30 India time, then 14 Feb 2028). Clearing cookies or opening a private window also gives a fresh trial; the 40 a day per-address cap, the one-minute limit and the global budget still bound that. The limits are counted in the order burst, trial, address, signed-in day, global, so when the global budget is used up an anonymous message has already spent a trial hit: after two attempts that visitor sees the sign-in gate instead of "unavailable". Do not diagnose the budget from the screens a visitor sees; use the counter query below. Pressing Send on a confirm card is not a chat message and does not use any of these five limits. It meets the limits of the action it runs: an enquiry is `sendEnquiry`, scope `enquiry`, 10 a day per user; a site visit is `submitProjectLead`, scope `project_lead`, 5 an hour per visitor (`src/server/rate-limit/limits.ts`). A customer over either limit sees the card's "please wait" line. The card adds no limit of its own (`src/features/ai-chat/action-config.ts`).

**How close is today.**

```sql
-- The last 7 days of the global counter (older rows are swept). window_start is the UTC day.
select window_start, hits
from public.public_rate_limits
where scope = 'ai_chat_global_day_global'
order by window_start desc
limit 7;
```

Messages left today = the budget minus `hits` for the row whose `window_start` is today's UTC midnight (05:30 India time). `hits` keeps counting after the budget is reached, so `hits` above the budget is the number of messages turned away. These rows count UTC days, so a per-day count from the queries in section 4 (India dates) will not match one counter row exactly. If `RATE_LIMIT_HMAC_SECRET` is ever changed, the counter's key changes too: the budget restarts that day and this query shows two rows for one day.

**What the customer sees at the limit.** The chat shows the "unavailable" state (HTTP 429, state `unavailable`): "The AI assistant is unavailable right now. It has reached its limit for today. Search by locality, type, bedrooms and budget instead." The other limits show their own screens: the sign-in gate after the free messages ("Sign in to keep chatting"), "Too many messages in a short time" with the seconds to wait, and "Too many messages for today" for the address backstop and the signed-in day. A limit that fails to count (database or secret problem) shows the generic error screen and nothing is let through.

**The alert.** **No automatic budget alert exists in the repository** (not built, not verified anywhere). Until one is built, the owner looks: the global-counter query above and the "which limit refused" query in section 4, once a day in the first week and after any cost worry. Ask the provider's dashboard for its own spending limit and email alert (recommended; the screens are **not verified** here). A daily message budget does not cap tokens per message: cost per message comes from the cost query in section 4 and the measured numbers of task AI-P8-T03, which are **not measured yet** (the spike results table in `docs/runbooks/ai-spike.md` is empty).

**Changing the budget.** A pull request that edits the one constant (a settings-that-cost-money change, class C2: owner decides), merged, then deployed. To stop all spending at once do not edit the budget: use the kill switch (section 3).

## 6. Switching provider

**What is built.** `openai` (the adapter `src/server/ai/openai.ts`, over the Responses API, stateless, one tool call per round until the real-key run passes) and `fake` (tests and local work). `gemini` is an accepted name but has **no adapter**: `AI_PROVIDER=gemini` today makes every message fail with "not wired yet".

**Changing the model inside OpenAI** (a new model id):

1. Run the real-key conformance run with the new id (below).
2. Run the golden and red-team sets on it and compare with the last accepted model (the eval harness is task AI-P8-T01; **after AI-P8-T01 is merged, check this section** and name its command here).
3. Have a Tamil and Tanglish native reader look at the answers.
4. Redo the cost query (section 4) on a day of dev traffic and check the daily budget still fits.
5. Owner sets `AI_MODEL` in Vercel and redeploys. Usage rows carry the model, so the two models can be compared by the queries in section 4.
6. To go back: set the old id and redeploy.

**OpenAI to Gemini** (the checklist of ADR-128 section 4.4):

1. **A new adapter** in `src/server/ai/` (`gemini.ts`), with Google's official package: its own pull request through `/add-dependency`, owner's approval. A new key variable will be needed; its name is **not decided**.
2. The **conformance suite** (the same scripted conversations that run against the fake) must pass against the new adapter over mocked HTTP in CI, then with a real key. The shared suite is `src/server/ai/__tests__/conformance.ts`; the OpenAI mocked run is `src/server/ai/__tests__/openai.conformance.test.ts`.
3. The golden and red-team sets, Tamil and Tanglish review, new cost and daily budget (as above).
4. Update the privacy policy's processor list, the cookie and consent wording if affected, and the processors row in `docs/engineering/security.md`. The provider's retention, training-use and data-location terms are read by the owner and the legal reviewer first (gate G-H).
5. Roll out behind the flag; keep the old provider's variables in place so the switch back is one variable (`AI_PROVIDER`) and a redeploy. There is **no automatic fallback** between providers in the first release.

**The real-key runs that already exist (owner runs them; agents never do).**

- The comparison spike: `docs/runbooks/ai-spike.md`, sections 3 and 4: `node scripts/ai-spike/run.mts --dry-run` (no keys, no network), then `--provider openai --limit 2`, then the full run. It uses its own `AI_SPIKE_*` variables, not the app's.

## 7. Incidents

Steps are in order. "Owner" means the owner does it; "agent" means an agent session may help by reading code and opening a pull request. **Switching the flag off is always allowed first** (a confirm card already open can still be sent for up to 30 minutes: section 3) and costs nothing but the chat being absent.

### 7.1 The provider is down or very slow

Signs: many `error`, `fallback` or `aborted` outcomes with `fallback_reason` `provider_error` or `time_limit`; customers see "I couldn't finish that. Try a simpler question, or use the search filters." with a link to `/properties`, or "We couldn't answer that".

1. **Owner:** run the outcome-per-day query and the caps-and-fallbacks query (section 4) for the last hour (change the interval).
2. **Owner:** check the provider's own status page and your account page (addresses **not verified** here; find them from the provider's site). Check the key has not been revoked or run out of credit.
3. A transient failure is retried once by the loop; a longer outage is not worked around: there is no second provider. If it lasts, **owner** switches the flag off (section 3) and switches it on again when the provider recovers and one test message works (check D5).
4. **Agent:** if the logs show our side (not the provider), find the request by the `x-request-id` header or the `requestId` field of the log line (`ai chat failed`, `ai agent gave up on a round`); no message text is in a log line.

### 7.2 A cost spike

Signs: the global counter near the budget early in the day; many messages from one anonymous visitor; the provider bill or its alert.

1. **Owner:** the global-counter query and the abuse query (section 4).
2. **Owner:** if it is abuse from one source, the limits are already bounding it (2 free messages per browser until cookies are cleared, 40 a day per address, 10 a minute). If it is wider, switch the flag off.
3. **Owner:** if a key may have leaked, make a new key in the provider dashboard, put it in Vercel, redeploy, then delete the old key.
4. **Agent:** propose a lower budget or limit as a pull request (section 5); the human check used for phone codes can be added to the anonymous path if abuse continues (ADR-128 section 7.1).
5. After the event: write what happened and the numbers in the pull request that changes the budget.

### 7.3 A suspected prompt injection or leak

Signs: output tags `prompt_leak`, `internals_leak`, `contact_blocked` or `competitor` suddenly frequent; `injection_suspected` or `internals_probe` bursts; a customer report that the assistant gave a phone number, a link, another portal's name or said how it is built.

What protects the customer even if the model misbehaves: the model has no write tool, no web tool and cannot make a link; contact details must come from this turn's tool results; the prompt holds no secret (only rules and a random canary). So the worst case is a wrong sentence, not an action or a leak of data. One exception since the confirm card: the two propose tools only sign a proposal and write nothing, but a customer's click on **Send** can send the enquiry or visit request the model drafted. Three things limit that: the card shows the message, the name and the phone number (from the account, never from the model) before anything is sent; only the click sends, and typing in the chat never does; and the send re-checks the signed proposal for the customer of that request and runs the customer's own enquiry or lead rules (`src/features/ai-chat/confirm/send.ts`). So the worst case is a message the customer did not read closely before pressing Send.

1. **Owner:** run the rule-tag queries (section 4). A rule that fired means the check worked; a customer report of something the checks should have caught means a gap.
2. **Owner:** if a real gap (a wrong number given as fact, a phone or link that no tool returned, a description of how it is built reached a customer), switch the flag off.
3. **Preserve evidence:** only the request id, the time and the rule names exist, by design; the customer's own words exist only on their screen. Ask the reporter for the time and a screenshot (they choose what to share). Never ask a customer to send a secret.
4. **Agent:** add the case to the red-team set (task AI-P8-T01's files, **after it is merged, name the path here**) and the guard tests, fix forward through a normal pull request with a fresh-context review; the prompt version string changes with any prompt edit.
5. If a key or secret appeared anywhere, rotate it (the provider key as in 7.2; `RATE_LIMIT_HMAC_SECRET` changes every visitor's hashes, so every free trial restarts, the global budget counter restarts that day, and proposals in flight become invalid).
6. Suspected exposure of personal data: `docs/runbooks/release-and-rollback.md` section 8.3 (rotate keys, review `audit_log`, assess duties with counsel).

### 7.4 A customer complaint

1. Ask for: what they asked about (not needed word for word), the approximate time in India time, whether they were signed in, and a screenshot if they are willing.
2. **Wrong answer about a home or project:** the tools read the same cached public reads as the pages, so check the page itself; the answers can be minutes old (the tool results carry an "as of" time). A wrong fact is a bug or a stale cache, not memory in the model.
3. **Refusal that seems wrong:** find the rule from the tags around that time (section 4, no text); a false positive is fixed by editing one list in `src/config/ai.ts`.
4. **"I typed my phone number":** the input check replaced phone and email, Aadhaar-like, PAN and card-like numbers with a placeholder before the model saw them, and the chat shows a notice that personal details were removed. It does not catch names or addresses. What the provider keeps is set by its terms (not verified). The chat itself stores nothing beyond the usage row (an enquiry or visit request the customer sends from a confirm card stores its message in the normal enquiry or project-lead records, like one sent from the form).
5. **A signed-in customer asks what was recorded:** the owner can read that account's usage rows by `user_id` in the SQL Editor (names and numbers only). Their enquiries are in the existing enquiry records, as without the chat.
6. **An enquiry or visit sent through the chat that the customer did not mean to send:** the card's Send button is the only way to send, and the send uses the existing enquiry and project-lead actions, so the record is a normal one (the customer sees their own enquiries from the card's link to `/dashboard?tab=sent`). The usage row cannot show it (it holds counts and tags only), and the send passes nothing that marks the chat as its source (`src/features/ai-chat/confirm/send.ts`), so the record looks like one sent from the form. One proposal sends once: the proposal's own id is the idempotency key, so a second click, a second tab or a replay makes no second record. Ask the customer for the time of the send and the home or project; whether a customer or the owner can withdraw an enquiry or lead, and what the audit trail records for it, are **not verified** here (read the enquiries and projects runbooks and the admin screens before promising anything). If the complaint is that the model drafted a wrong message, treat it like 7.3 (a wrong sentence) and add the case to the red-team set.

### 7.5 The chat refuses everyone, or the counter fails

Signs: every message ends in "We couldn't answer that"; logs show `ai chat failed`. Likely causes: `RATE_LIMIT_HMAC_SECRET` or `SUPABASE_SERVICE_ROLE_KEY` missing or wrong, the provider variables missing, the database unreachable. Check the variable **names** in Vercel, redeploy, and check `/api/health`. The chat fails closed on purpose: nothing is let through unchecked. Switch the flag off while fixing.

## 11. SPK-03: the forwarded-address check on the dev site (AI-P8-T03, 16 Nov 2026)

Run against the dev address only (`https://finds-prop-app.vercel.app/api/ai/chat`), the owner having approved at most 10 requests. Six were attempted with the same `curl` program and the body `{"messages":[{"role":"user","text":"nobroker"}]}` (the input check refuses it: no model call, no cost). The `visitor_hash` of each usage row was read afterwards (first 8 characters).

| Request                                    | `visitor_hash` start                       |
| ------------------------------------------ | ------------------------------------------ |
| No extra header                            | 5778b213                                   |
| `x-forwarded-for: 203.0.113.9` only        | 5778b213                                   |
| `x-vercel-forwarded-for: 203.0.113.9` only | 5778b213                                   |
| `x-forwarded-for: 198.51.100.7`            | 5778b213                                   |
| `curl -4` (forced IPv4), no extra header   | 5778b213                                   |
| `curl -6` (forced IPv6)                    | not sent: no IPv6 route from this computer |

**Result: a made-up forwarded header does not change who the app thinks the caller is.** All five requests that reached the app have one hash, so neither `x-forwarded-for` nor `x-vercel-forwarded-for` from outside is trusted (what ADR-033 expects of Vercel). Two earlier plain requests from the same program gave the same hash. A different program on the same computer (Windows `curl.exe` instead of the MSYS `curl`, so a different browser string) gave a different hash, which is expected: the hash mixes the address and the browser string.

**Not shown by this run:** that a caller on a different public address gets a different hash (the hotspot step of D11). Only one address was available, and the hash includes the browser string, so the program difference above is not proof. The code reads `x-vercel-forwarded-for` first, then `x-forwarded-for` (`src/server/rate-limit/visitor-hash.ts`), so there is no sign that a customer can set the address the limit uses; that the limit follows the real address is shown only by the code reading, not by this run. **Owner step, advised before launch:** do the hotspot step of D11 once with one program and see a different `visitor` in the rows. The spoofing test passed on one address and one program; address-dependence is untested, so SPK-03 stays open until that last step.
