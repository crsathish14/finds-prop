# Stage 0 · Acceptance criteria per feature (S0-T07)

> Copied from the implementation plan on 31 Oct 2026 and now maintained here (HD-11). References to plan documents (`06`, `07` and so on) point to the archived plan.

Testable acceptance statements for every requirement in `01-requirements-and-scope.md`. They are the _business-level_ definition of "this feature works"; the Definition of Done (`13`) adds the engineering checks (tests, security, accessibility) that apply to **every** feature.

How to use: a slice is accepted when every numbered statement for its `FR-*` rows is demonstrably true (by a test or a recorded manual check) at 390, 820 and 1440 px. Numbers in brackets refer to Phase 1 business rules (`BR-*`) or UX documents. UX screen keys are in `final-ux/screens/`.

## 0. Applies to every feature

- G1. Every state designed for the screen exists: default, loading, empty, no matches, validation error, success, failed action, auth required, confirmation, rate limited, not found (where the UX has it).
- G2. Typed input is never lost on failure; errors name the problem and the next step; the first error gets focus.
- G3. Irreversible actions ask for confirmation; reversible ones offer Undo or nothing.
- G4. Works with keyboard only; visible focus; screen-reader names and live regions as in `final-ux/interaction-specifications.md` §14.
- G5. No horizontal overflow at 390 / 820 / 1024 / 1280 / 1440 px.
- G6. Authorisation holds at three layers (UI, server, database); another user's record returns "not found".
- G7. No personal data, secrets or tokens in logs, URLs (other than the allowed search/redirect parameters) or error messages.

| FR-SYS-01 Rate limiting      | Limits are enforced atomically in the database with the values in `07` §11; the visitor is identified only by a salted hash, never by raw IP.                                                                                      |
| FR-SYS-02 CRM retry job      | The scheduled job is armed while retries are pending and disarms when none remain; the target URL comes from configuration per environment; the endpoint only runs with a valid token.                                             |
| FR-SYS-03 Event tracking     | Events are recorded without accounts, de-duplicated and limited as in FR-PUB-09.                                                                                                                                                   |
| FR-SYS-04 Form pipeline      | A submission is validated on the server, stored, rate-limited, optionally forwarded to the CRM, and mirrored into project leads when name and phone are present (BR-63); a repeated request with the same key is not stored twice. |
| FR-SYS-05 Storage limits     | Each bucket has its size and file-type limits set on the bucket itself and the access rules in `07` §6; unfinished uploads are cleaned up.                                                                                         |
| FR-SYS-06 Audit log          | Moderation, role, builder, CRM and CMS changes create an audit entry with who, what and when; entries never contain secrets; only the admin can read them.                                                                         |
| FR-SYS-07 Seed data          | A single command creates fictional Tamil Nadu sample data locally and refuses to run against anything that is not local or an allow-listed dev project.                                                                            |
| FR-SYS-08 Public projections | Public responses and direct database reads by visitors never include the owner id, rejection reason or moderation columns.                                                                                                         |
| FR-SYS-09 Legal pages        | Privacy, Terms and Cookie pages exist and are linked from the footer and from the sign-in, enquiry and lead forms before launch.                                                                                                   |
| FR-SYS-10 Health             | A health endpoint reports OK or not OK for the app and database without exposing secrets.                                                                                                                                          |
