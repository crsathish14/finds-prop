# ADR-125 · Authorization verification (S8-T04)

- Status: Accepted (verified in CI: part 1, the database, in #181; part 2, the actions and the route handlers, in #188)
- Date: 2026-11-11 (updated 2026-11-12)
- Related: ADR-017 (column grants), ADR-028 and ADR-123 (the audit log), ADR-097 and ADR-121 (functions that run as the caller), plan 07 sections 4.2, 4.3 and 5, `DB-RLS-matrix`, `DB-PRIV`, BR-30 to BR-35, R-BE-03, R-BE-04, R-BE-13
- Plan for S8-T04 approved by the owner on 11 Nov 2026 ("approved"), without the second-factor ("aal2") variants (see "Out of scope"). The plan for part 2 was approved on 12 Nov 2026.

## What this is

Stage 8 asks for the authorization of the whole system to be checked end to end, not table by table as it was built. Part 1 is the database: two pgTAP files that say, in one place, who may do what, and fail when anything drifts. Part 2 is the server: a pinned inventory of who may call each Server Action, a check that every action that takes an id answers a wrong owner with NOT_FOUND, and the refusals of the six route handlers. The three layers of authorization (the page's hint, the server's check, the database's rule) are now each tested on their own.

## Decision

- **`rls_matrix.test.sql`: three layers over every public table.**
  1. **Privileges.** For each of the 23 tables, the privileges `anon`, `authenticated` and `service_role` hold (select, insert, update, delete, truncate; select, insert and update count when held on any column, as the column grants are). Neither `anon` nor `authenticated` holds truncate anywhere (the service role does, on every table but the audit log, which is the platform default for the server-only role and the same on the hosted project); `anon` holds select only, on the tables the public site reads; the audit log has select for the admin and nothing else for any role (it is written only by definer functions).
  2. **What each person can see.** Seven people (a visitor; customers A and B, each with a verified phone; active builders A and B; an inactive builder C; the admin) each read the fixtures of every table, and the list of rows each can see is compared with the policy table of plan 07 section 5. It includes the cases that matter most: customer B cannot see customer A's draft or pending listing, nobody but the two parties and the owner sees an enquiry, a builder sees only their own projects, units, leads and events, an **inactive builder sees none of their own pending projects** (the immediate effect of deactivation), a visitor sees only approved listings and live projects, and the server-only tables (secrets, tokens, rate limits, idempotency keys, app configuration) are invisible even to the admin through a client.
  3. **What each person can write.** About a hundred writes are tried as the person named and always undone: an edit, a delete or an insert that would succeed for the right person, so that a refusal is the policy's and not a typing mistake. Each is shown with its result in the test's name (`yes`, or `no` with the reason: no privilege, a policy, a trigger, or no row changed).
- **Inventory guard.** The tables are compared with the list in the file: a new public table without a row in the matrix fails the test, so authorization is decided when a table is made, not found later.
- **`function_grants.test.sql`: who may run each public function.** Visitors: five read-only helpers (`listing_is_public`, `listing_label`, `project_is_live`, `public_project_form`, `search_properties`). Signed-in people: those plus the helpers the policies call and the functions the portals use, each of which checks the caller itself (32 more). Everything else is for the service role only, and no trigger function can be run by a visitor or a signed-in person. A new function, or a changed grant, fails the test until the lists are updated on purpose.
- **The hosted dev database was read, not changed,** to check that these lists are the real state and not only what the migrations say: the privileges on every table and function were read (catalog only, no row of data) and match. The one difference is below.
- **`action-access.test.ts`: who may call each Server Action.** The access level is written in each feature's `action-config.ts` and spread into its `actions.ts`, so the test reads the source and builds the table (it cannot import the actions without importing the whole server). It checks that every `defineAction` has a level, that the counts are **31 `super_admin`, 9 `builder`, 18 `verified-phone`, 8 `none` and 1 `user` (67 in all)**, and that all 67 names and levels equal a written list: a new action, or a changed level, fails until the list is changed on purpose, where a reviewer sees it. The 8 actions that need no sign-in are named with a reason each: `sendPhoneCode` and `verifyPhoneCode` (the visitor is not signed in yet; rate limited), `signOut` (ends the caller's own session), `submitForm` (the public forms: Turnstile, rate limit, idempotency), `trackProjectEvent` (a counter that stores no personal data), `readSavedHomes` (an empty answer for a visitor), `readChatCardsAction` (AI-P5-T02: a read of at most three public cards for the references of a chat answer, through the public pages' own cached reads) and `startStaffGoogleSignIn` (starts the Google redirect; eligibility is decided in the callback). Every action with `My` in its name must be a `builder` action.
- **A wrong owner is NOT_FOUND, for every action that takes an id.** Each such action was checked for a test that shows it. Almost all had one in the integration tests (listings, my-listings, listing-edit, agent-role, media, enquiries, project-leads, forms, project-editor, units, leads, moderation and the admin features for a missing id). Two had none and now have: `saveHome` and `unsaveHome` (only a fake store had been tested; `tests/integration/saved.test.ts` now runs them against the database: a listed home saves once, a home waiting for review or a made-up id is NOT_FOUND and leaves no row, a second unsave changes nothing) and `finalizePhoto` (a path in the caller's own folder for someone else's listing is NOT_FOUND and records nothing). `updateMyProfile`, `createMyProject` and `createListingDraft` take no foreign id: the owner comes from the session.
- **The six route handlers refuse a caller that cannot prove itself.** `route-access.test.ts` calls the real route files (`crm-retry`, `sweep-media`, `health`, `auth/callback`, `auth/confirm`) and the existing `send-sms` route test is extended. `crm-retry` and `sweep-media`: no token, an empty token, a wrong token, a token of another length, the token in the wrong header, a cookie only, and no stored token each give a plain 401 with `no-store`, and the only database call is the read of the token; a control with the right token is let in, which shows the refusals are because of the token. `send-sms`: a signature made with another key, a changed body, an old timestamp, missing headers, a cookie only, a bearer token only, and no secret configured each give 401. `health` is public by design: it exports GET only, reads no request and no database, and answers only `{status, app}` with `no-store`. `auth/callback`: a missing or unknown area, no code, a provider error or a failed exchange never reach a session; a customer is signed out and refused the admin area, and a foreign `next` address is ignored. `auth/confirm`: a missing, short or odd token, or the wrong type, goes to the expired page and Supabase is never asked.

## Findings

- **`public.rls_auto_enable()` is open to visitors on the hosted project and is not in our migrations.** It is Supabase's own event-trigger function (it switches row-level security on for each new table, and the project's `ensure_rls` event trigger runs it). It returns `event_trigger`, so PostgreSQL refuses to run it as an ordinary function (it can only be fired by the event), and it pins its `search_path`. No action is needed, and it is left alone (it is a platform feature that protects new tables). The catalogue test leaves event-trigger functions out for this reason; the local and CI databases do not have it.
- **The admin cannot change a listing, an enquiry, a photo or a person's name directly,** only through the moderation and close functions, and only the owner moves an enquiry on. This is the design (the matrix records it as "no"); it is written here so that nobody takes it for a gap.
- **Results of the CI runs: no hole was found.** The matrix (339 checks) and the function catalogue (5 checks) pass, inside the whole suite of 41 files and 1,475 checks. The first runs showed three wrong expectations of mine, none a policy fault: the plan count was a bigint where pgTAP wants an int; the service role holds truncate on every table but the audit log (the platform default, the same on the hosted project; `anon` and `authenticated` hold none); and one project insert lacked the required locality, so it was refused for that reason and not the policy's (it and three "no" neighbours were fixed). Every row-visibility check and every other write case passed as first written.
- **Part 2 (#188): no hole was found either.** The two gaps above were missing tests, not missing checks: both actions already refused correctly, and the new tests passed as first written. The unit suite passed (360 files, 5,408 tests locally before the merge) and so did all 29 integration files. The first integration run failed before any test ran, because `supabase start` could not bind a Docker port (the known flake); the same commit passed on a rerun of that job.
- **What part 2 does not check.** Admin actions that take an id answer a missing id with NOT_FOUND in the crm, form-builder, leads, moderation, project-moderation, units and builder-invite tests; `updateProject`, `duplicateForm` and `retryCrmDelivery` were not checked one by one. The admin can reach every row, so "wrong owner" does not apply to them. A staff callback whose code gives no session goes back to the sign-in page with the "error" message, not "denied", and signs out: the browser is not told why in either case.

## Out of scope

- **The second factor ("aal2" variants of the matrix).** The roadmap lists them, but the owner decided on 1 Nov 2026 that staff sign in with Google only, with no second step (`docs/runbooks/staff-google-sign-in.md`). There is no aal2 condition in any policy, so there is nothing to vary. If a second factor is added later, the matrix gains an "aal1 admin" person.
- **A browser test of the pages' hints** (the first of the three layers) is the end-to-end journeys of S8, not this task.
- **Rate limits and Turnstile** are not authorization; their tests are in the rate-limit and forms suites.

## Consequences

- No migration, package, environment, CI, gate or protected-file change; two pgTAP files and five test files (new: the action inventory, the route handlers and the saved-homes integration test; extended: the send-sms route test and the media integration test). They read the real roles, policies and source, so they pass or fail with the migrations and the code.
- Adding a table, a policy, a grant or a function now means adding its row in the matrix, in the same change. Adding a Server Action, or changing who may call one, means changing the list in `action-access.test.ts`, and an action that takes an id needs a wrong-owner test.
- Rollback: delete the test files and this ADR.
