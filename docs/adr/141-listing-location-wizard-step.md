# ADR-141 · The location field in the post-property wizard (place search, plan PR 7b)

- Status: Accepted. Built and merged (#266, #267); the owner approved the new words as written (18 Nov 2026). This is the application half of the listing location: the database half (`set_listing_location()`, "submit needs a location") is ADR-138. The words listed under "New words" are approved.
- Date: 2026-11-18
- Related: ADR-060 (the wizard's server side), ADR-057 (answers kept before signing in again), ADR-132 (the screens, `LocationField`), ADR-133 (the route, `source=listing_form`), ADR-134 (the usage count), ADR-136 (the box and `usePlaceSuggestions`), ADR-138 (the database half), ADR-140 (how a form gets a connected island through a prop), DEC-09 policy C, DEC-35 (the exact point is private, the public point is rounded), FR-GEO-01 criterion 3, FR-GEO-02, `OLA_MAPS_PLAN.md` (outside the repository) decision D4, section 4.2 and PR rows 7a to 7c
- Class C2 (personal-data handling: an owner's private location). Owner decisions of 17 Nov 2026: a listing location is required to submit, the fallback is the middle of an area shown as approximate, no map, no new column, no Ola place id stored.

## Where the point lives, who can read it

- **In the database, in `properties.location`** (a PostGIS geography, longitude first), written only by `set_listing_location()` (ADR-138). No new column and no place id from Ola are stored. The generated column `public_location` is the same point rounded to 0.001 degree (about 100 metres); it is the only point that is ever public (DEC-35). Search, cards, the property page and "Also near" read `public_location` only.
- **Who can read the exact point:** the database and nobody else through the application. Owners and the admin can reach the row through `my_properties()` and `admin_properties()`, but no screen, query or action in this change selects `location`. A visitor and a signed-in person cannot select the column at all (grants). The browser never receives the exact point of a stored listing.
- **In the browser, for a moment only.** The point the owner picked is part of the wizard's state while the form is open (as text, with its name), because the owner chose it in that sitting. It is sent once to the server action. It is never put in an address, a log line, an error message, a cookie or `localStorage`. The only copy is inside the answers the form already keeps in `sessionStorage` when the session ends and the owner presses "Sign in again" (ADR-057): this tab, thirty minutes, removed when read. That keep is how a failed save and an ended session lose nothing.
- **In the server:** the action carries the point from the request to the RPC and nowhere else. The action's answer is `{ listingId, shortId, status, wentBackToReview }`; its log line holds the listing id and the status; no error message or field error holds a number.

## Decision

- **The step.** `AddressStep` (the wizard's Basics step) draws the connected location field above the Address, Locality, City and Pincode boxes; State stays read-only. The field is the search feature's island `ListingLocationField` (`src/features/search/listing-location-field.client.tsx`), which draws the approved `LocationField` (ADR-132) around the place search box. As in ADR-140 the listings feature cannot import the search feature's client code, so the post-property page gives the island to the wizard as a prop (`locationField`); the contract (`ListingLocationFieldProps`) is in `src/types/places.ts`. The hook gains a source (`listing_form`, counted under that name in the usage count) and an optional list of kinds.
- **What a pick fills.** A chosen suggestion is kept as the place and fills a box only while it is empty (spaces count as empty), never over what was typed: the address with the name and the rest of the address (cut to 300), the locality with the name when the suggestion is an area, the city with the first part of the address that is not the state, the country or a number, and the pincode with the first six-digit number that stands alone and starts with 5 or 6. The rules are pure functions in `wizard-state.ts` (`applySuggestion`, `applyArea`).
- **Exact or approximate.** A street or a venue is the exact spot. An area (a suggestion of kind `area`, or an area from the chooser) is the middle of the area and is held and shown as approximate, as the owner asked.
- **"Choose the area instead".** The field's second path asks the same route for suggestions and keeps only those of kind `area`. When suggestions cannot be fetched (`unavailable`, or "too many searches" in the area box) the field says so and offers the site's curated localities (the Homepage page's list, with their points) as a plain list, so posting never stops. If the site has no curated localities the box stays and says suggestions are not available; the owner can try again.
- **Required to continue.** Continue on the address step is held until a place is held, with the field's own "Add a location to continue." as the error, the step marked "Needs attention", and focus on the field (it is the first field with a problem). The same holds for "Review and resubmit" of a refused listing. A listing already in review or Live may be edited without one: an old listing has none, an unrelated change must not be held back, and adding one is a moderated change that sends a Live listing back to review (ADR-138), which the owner is asked about first like any other moderated change (`changesNeedReview` gets a `placeChanged` argument). "Save draft" never asks for a place.
- **City starts as "Chennai".** The City box starts with a value the wizard gave it. While nobody has typed in it (and it was not filled from a saved draft or the kept answers) a pick may replace that starting value; once typed, saved or restored it is the owner's answer and is never replaced. Without this a Madurai listing would keep "Chennai" unless the owner noticed. The owner may prefer the literal rule (a non-empty box is never touched); it is one flag.
- **When it is written.** The place goes to its own action, never into the draft's fields: after the draft is created or saved by Continue or "Save draft" (drafts are created on the first Continue, ADR-060), and again only when the owner picks another place (the wizard remembers the key of the point last written, in memory). A failed save keeps the point in the form state; the next Continue writes it. A place the server refuses is let go (the field asks again) and the step stays open.
- **The action.** `setListingLocation({ listingId, lat, lng })` is built with `defineAction`: `verified-phone`, schema `setListingLocationSchema` (the listing id and two finite numbers in range; anything else in the request is dropped, so nothing in it can say who owns the listing or what state it is in), identity from the session, the existing `project_save` rate-limit scope (60 an hour per user; no new scope and no migration), no idempotency key (the same point twice leaves the same listing). It looks the listing up through `my_properties()` first (a foreign or missing listing is `NOT_FOUND` before anything is stored), then calls the RPC and maps its stable errors: `listing.location_out_of_region` and `listing.location_invalid` are `VALIDATION` with a `location` field error, `listing.not_found` is `NOT_FOUND`, `listing.not_editable` is `CONFLICT`, `listing.not_allowed` is `FORBIDDEN`. A Live listing that goes back to review (policy C) refreshes the site's tags for that listing; for a draft or a listing in review nothing public changes and no tag is refreshed. `submit_listing`'s `listing.location_required` is mapped to the same `location` field error.
- **The edit flow without exposing the point.** `getMyDraft` asks the database whether a place is stored with a filter (`my_properties()` selecting only `id`, `location is not null`), so the point is never selected, and the page hands the wizard one boolean (`hasLocation`). No migration, function or column was needed. A listing that holds a place shows the field in its "Location found" card with the words "Your saved location" and Change; the owner does not see a spot because the browser does not have it. Pressing Change lets go of the held place and the owner picks another; an owner who changes nothing writes nothing.
- **Order when editing.** Saving an edit writes the changes first and the place after them: for a Live listing the place is the change that sends it back to review, and the listing must still be Live when the other changes are saved.
- **Design Lab.** The Seller board's wizard step 1 specimens and the `wizard-basics` whole-page preview draw the field (found, and with the error). Nothing else changes. The baselines that shift are listed in the pull request and come from CI pictures.

## New words (approved by the owner, 18 Nov 2026)

- `validation.locationOutOfRegion`: "That place is outside Tamil Nadu. Choose a place in Tamil Nadu."
- `postProperty.location.savedLabel`: "Your saved location" (the name on the "Location found" card of a listing that already holds a place)
- `postProperty.location.areaLabel`: "Area" (the label of the curated list)
- `postProperty.location.areaOption`: "Choose the area" (the empty first line of that list)

Everything else is the approved `domain.locationField.*` and `domain.places.*`, plus `domain.placePicker.placeholder` ("Search for a place") in the two search boxes.

## Decisions for the owner

- **The rate limit shares a scope.** `project_save` (60 an hour per user) is the nearest existing scope; a dedicated `listing_location` scope is a one-line addition to the rate-limit list and its line in `docs/engineering/security.md`, which this change does not touch.
- **The City box.** The reading above (the untouched starting "Chennai" counts as empty), or the literal rule.
- **A listing in review or Live may be edited without a place**, and adding one sends a Live listing back to review. The prompt for old listings (7c, addendum below) is where that is explained before the owner confirms.
- **The field's red asterisk** is drawn on every use of `LocationField`, including that optional edit; it is the approved part and was left as is.
- **Curated areas.** The fallback is only as good as the Homepage page's list. The site's default list is empty; the live site has one.

## Consequences

- A listing posted through the wizard now has a point, so it appears in radius, distance and map-box search (ADR-135, ADR-137) once approved, with the rounded point only.
- Typing three characters in the address field calls `/api/places/autocomplete`, which is rate limited (ADR-133), counted as `listing_form` (ADR-134) and can be switched off with `PLACES_DISABLED=1`; with it off the owner is offered the curated areas and posting continues.
- The text typed is sent to our route and from it to Ola Maps, as the privacy page already says for the search box (ADR-136). The place itself is stored by us, not by Ola; no Ola id is kept.
- Rollback: the field is one prop. Without it the step has no place, and the database refuses a new submission (ADR-138), so this change and ADR-138 belong on `develop` together.

Lint, types, formatting and the policy checks. Not run, by the owner's rule: pictures, axe, the keyboard specs of the Design Lab (CI), Docker, the integration tests and the real RPC. ## Addendum (18 Nov 2026): the prompt for old listings (plan PR 7c)

Class C1: it wires the approved `LocationPrompt` (ADR-132) into the page; no migration, no function, no dependency.

- **Where and when.** `MyListingsTab` (the My listings tab of the dashboard) draws one `LocationPrompt` above the list while any listing of the owner in review (`pending`) or Live (`approved`) has no place stored. It counts them, and "Add location" leads to `/post-property/{id}` of the newest of them, which opens the wizard in its edit flow, where the field of this ADR is on the address step. After the owner saves, My listings is shown again with the next one, until none is left; the note then stops by itself. "One time" is read as one note for all the listings, not one per listing, and gone once it has done its job. There is no "dismiss", and nothing about it having been shown is stored (that would need a table or a column).
- **Which listings.** Drafts are not counted (the wizard asks for a place before a draft can be sent). Rejected listings are left out: they cannot be sent again without a place, and the wizard says so. Sold and rented listings are final.
- **How it is read without reading the point.** `getListingsWithoutLocation` asks `my_properties()` for `id, status` with the filter `location is null`, in the two states, newest first, up to the same 200 as the list, with the database's own count. The point itself is never selected (DEC-35).
- **The one new line.** When any of them is Live the note adds: "A live listing goes back to review when you add its location, and shows again once it is approved." This is what the Decisions section above promised the prompt would say; the owner approved it as written on 18 Nov 2026; the rule itself is ADR-138's (policy C), unchanged. It is the only new wording; the title, the body and the action are the approved ones. The Design Lab board shows the prompt with and without it (pictures from CI).
- **Verification.** Unit tests: the read (the filter, the states, the order, the count, the Live flag, a failed read logs the code only); the tab (no note when all hold a place; one note above the list with the count and the link to the newest; the review line only when one is Live; the empty state and a visitor); the component with and without the line.
