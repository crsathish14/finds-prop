# ADR-138 · A listing's location: `set_listing_location()` and "submit needs a location" (place search, plan PR 7a)

- Status: Proposed. The owner approved the overall plan and the decision on 17 Nov 2026 (`OLA_MAPS_PLAN.md` decision D4, PR table rows 7a to 7c): a location is required to submit a listing, with an area fallback (the centre of the area); no map; no new columns; no Ola place id is stored. This change is only the database part and merges when its checks pass and the owner accepts it.
- Date: 2026-11-17
- Related: ADR-060 (a listing may be submitted without coordinates; this replaces that for new submissions only), ADR-024, ADR-017, ADR-135 (distance sort), DEC-09 policy C, DEC-35 (the exact `location` is private, `public_location` is its generated copy rounded to 0.001 degree), FR-GEO-03, R-DB-01 to R-DB-07

## Why

No application code writes `properties.location`; only seed data does. Listings made through the wizard therefore have no point and are invisible to radius, distance and map-box search (ADR-135, ADR-137). ADR-060 allowed submitting without coordinates because the wizard had no way to give one. Plan PR 7b adds that step; this change is the database half.

## Decision

- **A function, `public.set_listing_location(p_property_id uuid, p_lat double precision, p_lng double precision) returns text`.** It is the write path the app uses for `properties.location` (the wizard step, PR 7b, and the prompt for old listings, PR 7c). It stores `st_setsrid(st_makepoint(lng, lat), 4326)::geography`, longitude first. `public_location` follows because it is a generated column (about 100 m, DEC-35). It returns the listing's status after the change.
- **`security invoker`, with no grant or policy change.** Owners already hold the update grant on `location` and the update policy limits them to their own rows, so the function needs no extra rights and `properties` gets no new grant. The identity is `auth.uid()`; ownership is asked of the existing definer helper `owns_property()` (users cannot read `owner_id`). A foreign listing, a missing listing and one the caller cannot see all answer `listing.not_found` (`P0002`). A caller with no session or no verified phone gets `listing.not_allowed` (`42501`), like the other owner functions. Execute is granted to `authenticated` only (revoked from `public`, `anon` and `service_role`).
- **Not a table-level lock.** The owner's column grant on `location` stays as it was; revoking it would be a grant change outside this PR's scope. The function is the supported path and the only one the app uses; the policy C trigger below applies to a direct update too, so the moderation rule cannot be skipped by it.
- **Which listings.** Draft, pending and rejected listings are changed and keep their status. An approved listing is a moderated change: the existing guard (`guard_properties`, policy C) already sends an approved listing back to Pending when `location` changes, exactly as for a title, description, type or address change, and the audit trigger records it. The function does nothing special for it and returns `pending`, so the screen can say so. Sending the same point a live listing already has changes nothing and returns `approved`. Sold and rented listings are closed (`listing.not_editable`, `55000`). This also means adding a location to an old live listing that has none sends it back to Pending until the admin approves it again; PR 7c must say so before the owner confirms.
- **The point is checked.** Both numbers must be present and finite, latitude within -90 to 90 and longitude within -180 to 180 (`listing.location_invalid`, `22023`), and inside the region bounds of the site setting `region` (`bounds.south`, `north`, `west`, `east`; the corners are inside; `listing.location_out_of_region`, `22023`). If the setting has no usable bounds (missing, not numbers, or south above north or west above east) the region is treated as unset and only the numeric range is checked. `site_settings` is public by design, so the function reads it with the caller's rights.
- **Submit requires a location.** `submit_listing()` is made again (same signature) and refuses a draft or rejected listing with a NULL `location` with `listing.location_required` (`23514`, the family of `listing.incomplete` and `listing.no_photo`), after the completeness check and before the photo check. The area fallback (the centre of the chosen area) is applied by the wizard through this same function, so the database sees an ordinary point.
- **Not retroactive.** `properties_complete_unless_draft` is not touched. Drafts, pending and live listings without a location stay valid and keep appearing in keyword and locality search, with no coordinates, and out of radius and distance results. Only a new submission (draft or rejected to Pending) is refused when the location is missing.
- **Existing tests.** `listing_submit.test.sql` asserted that a listing without a location can be submitted; it now asserts the refusal (`listing.location_required`), and the later search checks move listing 3 on as the system, as a legacy live listing. `function_grants.test.sql` lists the new function among those a signed-in person may run.

## Consequences

- Until PR 7b merges, the wizard has no location step, so a listing submitted through it is refused with `listing.location_required`. The action's error mapper already turns `23514` into a generic validation error. 7b should follow this PR closely and the two should reach dev together; if the owner needs the wizard to keep working in between, 7b must merge first with the step optional, which this PR does not allow.
- Moving the pin of a live listing takes it out of public results until it is approved again. That is the moderation the owner asked for (a pin on a different street is a change a moderator should see).
- No data is changed by the migration. Existing listings without a location are not found by radius search until their owners add one (PR 7c).
- Rollback: nothing is stored or removed. To undo, drop `set_listing_location(uuid, double precision, double precision)` and make `submit_listing` again as in `20261107140000_listing_submit.sql` (without the location refusal) in a new forward migration, after PR 7b stops calling the function. Locations already stored stay.

## Verification

- pgTAP, `listing_location.test.sql` (53 checks): the function is an invoker function with a pinned search path, not executable by a visitor or the service role and executable by a signed-in person; the owner sets a point on a draft, stored longitude first with `public_location` rounded within 100 m; refusals for a missing number, latitude out of range either way, longitude out of range, not a number and infinity, and points outside the region (including a good latitude with a longitude west of it), each leaving the stored point alone; a foreign draft, a foreign live listing and a missing listing all answer `listing.not_found`; a sold listing is refused; a pending and a rejected listing can be changed and keep their status; a live listing is left alone by the same point and sent back to review by another or by a first one, with the audit entry, and is out of public search until approved; no phone, no person in the session and a visitor are refused; unusable or upside-down region bounds count as unset; submit without a location is refused for a draft and a rejected listing, and works after the location is set; a live listing with no location is still returned by search with no coordinates and is left out of radius search; the public search returns the rounded point and has no column for the exact one, and neither a visitor nor a signed-in person can select `location`.
- `check:db` is run by CI (no Docker on the owner's machine); the regenerated `src/types/database.types.ts` comes from the CI job's own output.
