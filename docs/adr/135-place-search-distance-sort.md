# ADR-135 · Place search: the distance sort and the distance column in `search_properties()` (PR 5)

- Status: Proposed. The owner approved the overall plan on 17 Nov 2026 (`OLA_MAPS_PLAN.md` section 4.3, PR table row 5); this change is only the database part and merges when its checks pass and the owner accepts it.
- Date: 2026-11-17
- Related: ADR-012 (search architecture, the radius uses `public_location`), ADR-042 (search results), ADR-131 to ADR-134 (the other place search changes), DEC-35 (the public point is rounded to about 100 m), FR-GEO-03, BR-90, BR-91, R-DB-01 to R-DB-07

## Decision

- **A new sort value, `distance`.** `p_sort` accepts `distance` besides `newest`, `price_asc`, `price_desc` and `area_desc`. It is valid only when a place was given (`p_lat` and `p_lng`). `distance` with no place is refused with the error the function already gives for a bad sort (`search.invalid_sort`, code `22023`); `distance` with only one of the two coordinates is refused as an invalid place, as any search with half a place is. The nearest listing comes first; listings at the same distance are in id order, the tie-breaker every other sort ends with, so paging and the "show more" length stay stable. The four older sorts return the same rows in the same order as before.
- **A new last result column, `distance_km double precision`.** Kilometres from the given point to the listing's point, rounded to one decimal; null when no place was given. With a place, every row carries it whatever the sort is. The order uses the unrounded distance in metres, so the shown values never go down the page.
- **The point is `public_location`, never `location`.** `public_location` is the exact point snapped to a 0.001 degree grid (about 100 m, DEC-35). It is the only point a visitor can read (ADR-012, ADR-017), and the function runs as the caller, so it is also the only one it can use. A distance is therefore never more exact than 100 m, so showing it cannot be used to find a home more closely than the map point already does. A listing's private point is not readable by `anon` and is not used anywhere in the function.
- **Listings with no location** are still left out of every radius search (and so out of the distance sort, which needs a place) and are still found by keyword and locality text, with no distance.
- **The function is dropped and made again.** Adding a result column changes the return type, which `create or replace` cannot do. The migration `20261117130000_search_distance.sql` drops the function and creates it again with the same 17 arguments (names, order, defaults), `security invoker`, `stable`, the empty pinned `search_path`, the same explicit public columns and the same two-level query as `20261103110000_search_cover_after_page.sql` (the inner query counts, sorts and cuts the page; the outer one adds the cover). The grants are made again exactly as in `20261103100000_search.sql`: execute taken from `public`, given to `anon`, `authenticated` and `service_role` (`function_grants.test.sql` still holds the lists). Nothing else in the database depends on the function.
- **Still one statement with fixed texts.** The ordering text is chosen from five fixed strings; the caller's values travel as parameters. The distance is computed once, in the inner query, and only when a place was given, so a search without one costs what it did.
- **No TypeScript change here.** Only the generated types (`src/types/database.types.ts`) change. The sort options (`src/config/search-options.ts`), the URL schema, the screens and the AI tools do not send or show `distance` yet; that is PR 6. The app reads rows with a Zod object that drops unknown keys, so the extra column changes nothing until then.

## Consequences

- Nothing sends `distance` until PR 6, so on dev the change is visible only to a direct call of the function.
- With a 50 km radius at the planned scale, sorting by distance sorts only the listings inside the circle, which the existing radius test already limits; `total_count` is still `count(*) over ()`, so the cost of an unfiltered search is unchanged (ADR-012 spike findings). The spike script reads the statement from the function itself, so it follows this change.
- Rounded points mean several listings in the same 100 m cell have the same distance and are shown in id order. That is deliberate (DEC-35).
- Rollback: nothing is stored, so nothing is lost. Fix forward with a new migration that drops the function and creates it again as in `20261103110000_search_cover_after_page.sql` (without `distance` and `distance_km`) and repeats the same grants, after PR 6 (when it lands) stops sending `distance`.

## Verification

- pgTAP, `search_distance.test.sql` (39 checks): the result ends with `distance_km`, the function is still a stable, invoker function with a pinned search path and no private column, execute for visitors, signed-in people and the service role and not for `public`; the four older sorts and the default return the orders the search test expects; `distance_km` is null without a place and present with one; nearest first with ties in id order, a short page that starts the full order and the same `total_count`; hand-worked distances (0.0, about 6.7, 11.1 and 12.4 km) and the one-decimal rounding checked against the geography distance; `distance` with no place and `distance` with half a place are refused; filters and keywords combine; a listing with no location is never in a radius search but is found by keyword and locality, with no distance; no draft, pending, sold or rented listing is ever found; a signed-in owner gets approved listings only; the distance follows `public_location` (a listing 62 m from the point is 0.0 km away, not 0.1 km) and follows it when the private point is moved far away.
- `check:db` is run by CI (no Docker on the owner's machine); the regenerated `src/types/database.types.ts` comes from the CI job's own output.
