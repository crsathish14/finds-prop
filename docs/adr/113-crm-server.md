# ADR-113 · The admin's CRM connections: the server side (S7-T09, part A)

- Status: Accepted (the wording in the last section waits for the owner's confirmation)
- Date: 2026-11-10
- Related: ADR-034 (the hosted database changes only through db-deploy), ADR-100 (project moderation, the same shape of definer function), FR-ADM-09, SEC-07, BR-64 to BR-67, DEC-28
- Plan for S7-T09 approved by the owner on 10 Nov 2026 ("approved"): four parts. This is part A, the server foundation. Part B is the delivery engine and the retry route, part C the Lab parts, part D the `/admin/crm` page.

## Decision

- **A new `crm` feature, and two definer functions in the database.** The secrets live in a table that only the service role can read (BR-64), and a write made with the service role is recorded in the audit log as the system, not the admin. So the admin's save goes through `save_crm_integration(values, integration, secrets)`: it checks for itself that the caller is a super admin, writes the connection and any secrets it was given in one transaction, and the existing audit triggers record both with the admin as the actor (the names of the secrets that changed, never their values). `admin_crm_integrations()` lists the connections for the page with a yes or no for each secret and the number of forms that send to it. Neither function returns a secret. Delete is the admin's own policy on the table; the secrets go with the connection (cascade), the forms that used it keep working without it, and the delivery log is kept (the existing foreign keys).
- **A secret has three states.** Left out of the request: keep what is stored. Text: set it. `null`: clear it. A blank box on the screen is "left alone". A secret is 1 to 2000 characters on one line. Clearing a secret that was never stored writes nothing, so the audit log holds no empty entries.
- **The address check (`assertSafeUrl`, UT-crm-url).** An address is accepted only when it is https, has no sign-in details, is not an internal name (`localhost`, `.local`, `.internal`, `.lan` and the like, or a single word), and neither it nor any address its host name leads to is in a private, loopback, link-local (including the cloud metadata address), carrier-grade, documentation, multicast or reserved range, in v4 or v6 (mapped, NAT64, 6to4 and Teredo forms included). The platform's URL parser first turns the odd spellings (`2130706433`, `0x7f.1`, `0177.0.0.1`) into dotted form, so they are checked as what they are. A name that does not resolve is refused. The check runs when a connection is saved, when it is tested, and just before every delivery. Calls are sent with redirects off (a redirect is a failure), a 10 second limit and a 64 KB limit on what is read. Any port is allowed. **Known limit:** between the check and the connection a host could be pointed at another address (DNS rebinding); re-checking before each call, refusing redirects and the time and size limits keep this small, and pinning the checked address in the connection is a later hardening if the owner wants it.
- **Headers, body mapping and project codes** arrive as lists of rows (as the approved screen draws them, so a repeated name can be pointed at) and are stored as objects. A header cannot be one the server sets itself (`Host`, `Content-Length`, `Transfer-Encoding` and the like). Templates use `{{field_key}}` for the form's answers and `{{api_key}}`, `{{api_secret}}`, `{{access_token}}` and `{{lead_source}}` for the connection's own values; a name that is not known becomes empty. The body is sent as JSON. Everything shown or logged from an answer is cut to 500 characters and has every secret value blanked out.
- **A test sends a fixed test lead** ("Find Prop test", a phone of nine zeros after 9, an address ending in `.invalid`, a message that says it is a test) to the connection, active or not, and writes one line in the delivery log with no submission. The page is told only whether it worked, the CRM's HTTP status (or none) and how long it took. The test is the only thing that reads the secrets, with the service role, and it is limited like the admin's other decisions (`admin_decision`, 120 an hour), because it calls somebody else's server. No new rate-limit scope, so no change to `docs/engineering/security.md`; `features/crm/service` was already on the service-role allow-list.
- **Three actions** for a super admin, run as the signed-in admin (the test with the service role for the secrets only): `saveCrmIntegration` and `deleteCrmIntegration` (`admin_edit`, 600 an hour), `testCrmIntegration`. No idempotency key (a save sets values; a second delete finds nothing) and no cache tag (the connections are read for the admin alone and never cached).
- **The retry schedule** is a small pure helper (`retryDelayMinutes`, `nextRetryAt`; UT-retry): after a failed delivery numbered 1 to 5 the next try is in 1, 5, 30, 120 and 720 minutes; after the sixth there is none (BR-66). Part B uses it.
- **Types.** `src/types/database.types.ts` gains both functions, written by hand in the generated format; CI's database check compares it.
- **Not in this change:** the delivery engine, the retry route and the cron arming (part B), the screens (parts C and D), the delivery log read. Open for part B: what a pending submission of a deleted connection becomes (it loses its link and would stay pending).

## Wording to confirm (owner)

- `validation.crmUrlNotAllowed`: "Must be https and a public address." This is the approved screen's own text under the address box, used for every refusal of an address (not https, internal, private, does not resolve). The UX has no separate line for "we could not find this address".
- Two rows with the same header name, body field or project reuse the existing "Another row already uses this name." (`validation.localityLabelTaken`).
- The plain sentences kept in the delivery log when a call gets no answer ("The CRM did not answer in time.", "The CRM could not be reached.", "This address is not allowed: it must be https and public.", "The CRM tried to send the call to another address, which is not followed.") are the server's log text, not screen text; part D decides what the page shows.

## Consequences

- One migration and its pgTAP test (41 checks, run in CI); a feature with unit tests (the address check, the retry schedule, the sender, the schemas, the rules, the actions, the stores and the view) and an integration test (run in CI) of the save, the secret states, the audit trail, the test lead, the delete and a builder refused. The hosted dev database changes only through the db-deploy workflow, after the owner merges. No package, environment, CI or protected-file change.
- Rollback: drop both functions (`drop function public.save_crm_integration(jsonb, uuid, jsonb)`, `drop function public.admin_crm_integrations()`) and delete the feature. Connections already saved stay as ordinary rows.
