# ADR-137 · Place search on the results page: the distance choice, the distance on cards, "Nearest first" and "Also near" (plan PR 6)

- Status: Proposed. Built in this change; the owner approves before it merges. The look of the parts was approved from the Design Lab on 17 Nov 2026 (ADR-132, "Nearby homes").
- Date: 2026-11-17
- Related: ADR-012 (search architecture), ADR-040 and ADR-042 (the search address and the results page), ADR-132 (the screens), ADR-135 (the `distance` sort and the `distance_km` column), ADR-136 (the place search box), FR-GEO-03 (criteria 1 and 3), DEC-35, `OLA_MAPS_PLAN.md` (outside the repository) section 4.3, decision D5 and row 6 of the table of changes
- Class C1 (a feature inside existing patterns). Plan in the pull request. No migration, no new dependency, no map.

## Decision

- **Radius choice.** While the address has a place (`lat` and `lng`), the filter rail and the phone sheet show the "Search within" chips (2, 5, 10, 15 km; 5 when `r` is not in the address). Choosing one sets `r`; 5 is left out of the address by the contract's own rule. With no place there are no chips. A radius the chips do not offer (a curated place of 3 km, a hand-edited `r=7`) is kept and no chip is pressed for it until one is chosen. `FilterValues.radiusKm` is widened from the four choices to any number for that reason (a type change only).
- **Distance on cards.** `listingRowSchema` carries `distance_km` (a number, or null; absent in rows from before the column). `toPropertyCard` gives every home that has a number `distanceText` ("2.4 km away", the existing `domain.propertyCard.distanceAway`, one decimal). Nothing says which homes were placed only by their area (no column, owner decision D4), so the exact wording is always used and `distanceApprox` stays unused. A search without a place gets `null` from the function, so no card says anything.
- **Sort.** `distance` is a sort value of the address contract but not of the AI tool: `SORT_OPTIONS` keeps its four values (the AI `search_properties` tool still takes only those), and `ALL_SORT_OPTIONS` adds `distance` for the address. The address parser drops `sort=distance` without a place (the same rule as an out-of-range radius, so taking the place off, Clear all and a hand-edited address all fall back to Newest), and `toSearchRpcArgs` never sends `p_sort: "distance"` without a point, so the function's `search.invalid_sort` cannot be reached from the page. The results bar's and the sheet's sort lists offer "Nearest first" only with a place (`sortOptionsFor`). The default stays Newest.
- **Also near.** With a place, the main list is the homes inside the chosen circle (5 km by default). When it holds fewer than `NEARBY_THRESHOLD` (6) homes, the page reads `search_properties()` once more with the same filters, radius 15 km, sort `distance` and a page of 24, removes the homes already in the main list (by `short_id`) and shows up to `NEARBY_LIMIT` (12) of the rest in `NearbySection` ("Also near {place}", "{count} more homes within 15 km, nearest first.") under the main list, in the same grid or list view, each card with its distance. Nothing is drawn (no empty section, no gap) when the chosen circle is already 15 km, when the wider read adds no home or fails, when the main read failed, or when the address has no place name to say it by. The rules are pure functions in `src/features/search/nearby.ts`.
- **The count and the list agree (FR-GEO-03).** The headline count, "Showing n of N" and "Show more" belong to the main list only and are never changed by the section; the section's own note says how many homes it holds. When the main list is empty the empty state shows first and the section below it. While a new search is on its way the section steps aside, as the list does.
- **Both reads are the existing read.** The page calls `getSearchResults` twice, so the wider read is cached for minutes under the same tag as the main one (ADR-042) and an approval refreshes both. No new `use cache` was written; the wider read is simply another cache key (the parsed search with radius 15 and sort `distance`). `AGENTS.md` says search results are never cached while ADR-042 decided minutes under the listings tag; this change follows ADR-042 and flags the difference for the owner (see below).
- **The Design Lab does not change.** In the Lab's preview (`preview`) the screens show no chips and no "Nearest first", exactly as before, because its sample search has a place; the Lab's own "Nearby homes" entry draws these parts. The Lab's results board is not changed.
- **Words.** One new visitor-facing text: "Nearest first" (`domain.filters.sort.distance`). Everything else is the approved wording that already exists (`domain.nearby.*`, `domain.filters.radius.*`, `domain.propertyCard.distanceAway`).

## Decisions for the owner

- **Cached or not.** The two reads are cached for minutes, as the main read has been since ADR-042. If search results must never be cached (as `AGENTS.md` says), both reads need a change together, and that is a separate change.
- **A place with no name.** An address with `lat` and `lng` but no `place` or `locality` (a hand-made link) gets the chips, the distance on cards and Nearest first, but no "Also near" section, because its heading needs a name. This can be changed to a neutral heading if the owner wants new wording for it.
- **The chip row and a curated place's own radius.** A curated place with a 3 km radius shows no pressed chip until one is chosen (so the row never says 5 km while the search uses 3).

## Consequences

- Searching a place now makes one extra database read when its circle is small. With the cache that is at most one extra read per distinct search per few minutes.
- The AI chat tool is unchanged: it does not accept `distance`, and its rows now carry `distance_km` that it does not read.
- Left to later changes (plan): the listing location (PR 7), the admin pickers (PR 8), the AI tool (blocked on Ola's written answer about AI use). No map for now.
