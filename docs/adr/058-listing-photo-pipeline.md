# ADR-058 · The listing photo pipeline, server side (S6-T01, part 1)

- Status: Accepted
- Date: 2026-11-07
- Related: ADR-015 (media: buckets, the flow, public-read trade-off), ADR-024 (listing lifecycle, policy C), ADR-018 (rate limiting), `docs/engineering/security.md` 4.3 and plan 07 section 7 (secure uploads), DEC-09, DEC-26
- Plan approved by the owner on 7 Nov 2026, "All recommended": two pull requests (this one is the database and server; the browser side follows), 2000 px, quality 0.8, at most 6 photos, originals up to 20 MB before resizing, EXIF-bearing JPEGs refused on the server, and the orphan sweep as a scheduled job plus an internal route that the owner arms once.

## Decision

- **The flow is ADR-015's, built as three actions** (`src/features/media`): `requestPhotoUpload` (signed in with a verified phone; ownership, state and count checked first; counts the existing `upload_url` limit of 30 per user per hour; returns a one-time upload token for a path the **server** names, `<owner>/<listing>/<uuid>.<ext>`), the browser's upload to that path, then `finalizePhoto` (reads the stored file itself and records it, or deletes it and says why), and `removePhoto`.
- **The server trusts nothing the browser says about the file.** `inspectImage` reads the first bytes: JPEG, PNG or WebP only; an SVG, a GIF, an HTML page or a PDF is "not a photo" whatever it is called. It reads the real width and height from the header. The type found must match the extension the file was stored under. Sides must be 100 to 4096 pixels (the browser sends at most 2000; the server leaves room). Size is checked again (10 MB). An animation or a file cut short is refused. No image is decoded and nothing is fetched from a user-supplied address (plan 07 SSRF).
- **A file that still has camera metadata is refused, not repaired.** The browser re-encodes every photo, which drops the EXIF block and its GPS position. A JPEG with an EXIF segment, a PNG with an `eXIf` chunk, or a WebP with the EXIF flag or chunk therefore did not come from our page. The message is "could not be prepared, add it again". This follows the plan-07 rule that GPS in a photo can reveal the owner's home.
- **A refused file is deleted at once.** If the delete itself fails, the answer to the owner is still the real reason, and the sweeper removes the file within a day.
- **Only the server records a photo.** `listing_media` has no insert grant. `finalize_listing_media(owner, listing, path, mime, bytes, width, height)` is callable by the service role alone, so a signed-in user cannot name another user. It checks that the listing belongs to that owner and is not sold or rented, that the path is exactly `<owner>/<listing>/<uuid>.<ext>` for the declared type, and that the file is in the bucket. A repeat call for the same path returns the same row. The 6-photo limit, the cover and the "approved listing goes back to review" reset (policy C) are the triggers already on the table (`20261101130100`).
- **Where the caller's own rights apply and where the service role does.** Reading their listing, counting photos, asking for an upload token and deleting a photo row are done as the caller, under Row Level Security (the bucket policy of `20261101150200` also refuses another user's folder). Reading the stored file, deleting a refused file, calling `finalize_listing_media` and the sweep use the service role, in `features/media/service.ts`, which was already on the allow-list.
- **Orphans.** `orphan_listing_photos(hours, limit)` lists files in `listing-photos` older than 24 hours with no `listing_media` row (an upload never finished, a photo the owner removed, a deleted listing); folder placeholders are skipped. The route `/api/internal/sweep-media` deletes up to 500 per run through the storage service. The job `media-sweep` runs hourly and is started by `arm_media_sweep()`, the same pattern as the CRM retry: the job reads the site URL (`app_config`, `app.public_url`) and its token (`internal_cron_tokens`, `media_sweep`) at run time, so the token is never copied into the job. The route compares the `x-cron-token` header with the stored token in constant time, and answers a wrong or missing token with a plain 401. **The owner arms it once per environment** (`docs/runbooks/media-sweep.md`); until then nothing is swept, and nothing breaks.
- **Cache.** Adding or removing a photo can take an approved home off the site (policy C), so both actions refresh that home's tags (`tagsAfterListingChange`).
- **Not built, because no screen designs it:** reordering photos, choosing a different cover, alt text. The first photo is the cover, and removing the cover promotes the next one (database trigger). Columns for position and alt text stay as they are.

## Consequences

- Five new visitor-facing messages (**approved by the owner on 7 Nov 2026**), under `validation.*` in `en.json`: "Use a JPEG, PNG or WebP photo.", "This photo is too large. Photos can be up to {maximum} MB.", "You can add up to {maximum} photos.", "This photo is too small or too large in size. Try another one.", "This photo could not be prepared. Please add it again." No screen shows them until the browser side (next pull request) and the wizard (S6-T02).
- Nothing visible changes in this pull request. The pipeline is exercised by unit tests, pgTAP (`media_pipeline.test.sql`) and integration tests (`tests/integration/media.test.ts`); the last two run only in CI (no Docker on the owner's machine).
- `finalizePhoto` reads up to 10 MB into memory to inspect it, and is not rate limited on its own: each call needs an upload token that was issued under `upload_url`. If abuse shows, add a scope in `limits.ts`.
- The real-phone check of the browser resize and EXIF removal (S6-SPK-01) needs a page that hosts the uploader; the first one is the post-property wizard (S6-T02).
