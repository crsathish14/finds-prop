# ADR-188 · The enquiry actions send the mail (part 4 of the enquiry mail plan)

- Status: Accepted. Part 4 of the plan the owner approved on 24 Nov 2026 (`ENQUIRY_EMAIL_PLAN.md`). Part 5 (the runbook and one live send) follows.
- Date: 2026-11-24
- Related: ADR-181 (the Resend sender, the allowlist, the settings), ADR-183 (the editable wording and the render function), ADR-186 (`profiles.contact_email`), ADR-074 (the hook points this uses), R-BE-09 (adapters), R-BE-10 (no personal data in logs), DEC-26 (one enquiry per user per home per 24 hours), BR-72 (project leads: 5 per hour)
- Class: C2 (a new caller of an external provider, a new rate-limit scope, new read paths with the service role)

## Decision

- **When:** `sendEnquiry` (homes) and `submitProjectLead` (projects) call `after()` from `next/server` once the enquiry or the lead is **stored**. The visitor has already been answered, so they never wait for the provider. Inside `after()` the action hands over an event that holds an **id only**: `{ kind: "enquiry.received", enquiryId }` or `{ kind: "project_lead.received", leadId }`. (ADR-074's `enquiry.received` event carried a `listingId` too; it is dropped, because nothing needs it and the mail code reads the rest by the id.)
- **No mail when nothing was stored.** The hand-over is a hook (`onStored`) that `submitEnquiry` and `submitLead` call right after the database accepted the row. A duplicate within 24 hours, a home or project nobody can see, the owner's own home, a refused value, a rate-limited call, a repeat of the same form (the stored answer is replayed and the handler never runs) all end before it. A hook that throws is ignored, so the enquiry is never failed by the mail.
- **A notifier does the rest** (`src/features/enquiry-mail`, `createEnquiryMailNotifier`, an implementation of the `Notifier` interface of ADR-074). It asks the feature that stored the enquiry for the facts, then sends:
  - **Homes:** the enquirer's name and optional email from `enquiries`; the home's title, address and owner from `properties`; the owner's private address from `profiles.contact_email`.
  - **Projects:** the visitor's name and optional email from `project_leads`; the project's name and address from `projects`; the builder's address from `builders.email`.
  - **The reads are in each feature's own service file** (`enquiries/service.ts`, `projects/service.ts`), because those two files are already on the service-role allow-list (security.md 4.3) and the allow-list is not widened. The poster's private address and a builder's address are not readable by a visitor, and the action's request has ended, so the service role is the only way. The reads select **only** the columns the mail needs; the phone, the message and a visit date are never selected, so no mail code can leak them. Tests keep it that way.
- **The poster mail** says the enquirer's **name only**: no phone number, no message text, and no placeholder exists for either. **The enquirer's confirmation** is sent only when they typed an email (the field stays optional), for any kind of project lead including a site-visit request. A poster with no address on file (an existing home owner who has not added one, ADR-186) gets no mail; the enquirer's confirmation still goes, because the enquiry did reach the dashboard.
- **The wording** is the published template of each mail (`getMailTemplates`, ADR-183), filled with `renderMailTemplate`. If the saved wording cannot be read, or breaks a rule, the wording in code is sent and the log says which mail fell back (never the text).
- **The sender** is `chooseMailSender` with the real settings (ADR-181): nothing without a key, nothing from a developer's machine, only the allowlist on dev and staging, everyone on production.
- **A failure is only logged and ignored.** Each mail stands alone: if the poster's fails the enquirer's is still tried. A log line carries the request id, which mail, and an error code. For a provider failure it also carries the sender's own words (the HTTP status and the provider's short error name, such as `daily_quota_exceeded`; ADR-181 guarantees they hold no address or text). Any other error is reduced to its code. **No address, name, title, link or text is ever logged**; a test checks every line of every outcome.
- **The cap:** new rate-limit scope `enquiry_mail`, **20 notifications per poster per day**, counted by the poster's id (the home's owner or the project's builder, hashed before it is stored) under the database scope `enquiry_mail_key`. One enquiry counts once, however many mails it sends. Past the cap **neither** mail goes (the cap protects the poster's mailbox and the provider's 100-a-day allowance), the log says so, and the enquiry still shows on the dashboard. If the counter itself fails, the mail is skipped too (fail closed: a mail that is not sent costs nothing the visitor was promised). A new function `hitKeyedRateLimit` in `server/rate-limit` counts by a key after the request has ended. No migration: the counter accepts any scope name.
- **Nothing else changes for the visitor.** The action answers the same words as before.

## Default wording that now reaches people (unapproved)

The defaults of ADR-183 are what is sent until the admin publishes their own. One more piece of wording is new here: a home with no title is named **"a home"** in the mails ("... sent an enquiry about a home on findsprop", "We sent your enquiry about a home"). The owner must approve it, or say what to write instead. Projects always have a name.

## Consequences

- Nothing mails a real person until the owner verifies the domain in Resend and sets `RESEND_API_KEY` in Vercel (ADR-181); until then the no-op sender drops every mail and the log still shows what would have been sent.
- Two mails per enquiry means about 50 enquiries a day on the free plan (ADR-181). At 20 notifications per poster per day, one busy poster cannot use more than 40 of the 100.
- **A confirmation goes to an address the enquirer typed**, which anyone could type about someone else. It is limited by what already limits an enquiry: a verified phone, 10 enquiries per user per day (DEC-26), one per home per 24 hours, 5 project leads per visitor per hour (BR-72), and the poster's daily cap above. The confirmation holds no phone, no message and no name of the poster.
- The mail runs inside `after()`, which has no time limit of its own but is bounded by the platform's function limit; each send gives up after 3 seconds (ADR-181), and the worst case is two sends and three short database reads.
- A mail to a mistyped poster address bounces and is only seen in Resend's own log (ADR-186 noted this). A bounce handler is a later change if it happens.
- Rollback: remove the `after()` calls and the `onStored` arguments in the two actions; nothing else depends on them. The scope, the two finders and the feature can then be deleted. Stored rows and templates are untouched.
