# ADR-047 · SEO and metadata (S4-T10)

- Status: Accepted
- Date: 2026-11-05
- Related: ADR-025 (the URLs and the approved SEO decision, DEC-12), ADR-043 (the property page), ADR-046 (the projects pages), ADR-022 (environments), FR-PUB-14 and its acceptance criteria 1 to 4, BR-90 and BR-94 (what a visitor may see)
- Plan approved by the owner on 5 Nov 2026 as **one change** (the plan offered two; the owner chose one), with the recommended answer for each decision: a generated default share image, the canonical address keeps the filters and drops the view and sort, the structured-data types below, one sitemap file with a failed read answering an error, and the new words listed at the end.

## Decision

- **One place for what a page says about itself** (`src/features/seo`, pure and tested). `pageMetadata` builds the title, the description, the one canonical address, and the Open Graph and Twitter tags of a page. Paths stay relative; the root layout sets `metadataBase` from `NEXT_PUBLIC_SITE_URL` (its origin only), so every canonical link, share address and sitemap entry is made whole from the environment and never from a typed address. A page's `openGraph` replaces its parent's in Next.js rather than merging, so every page builds the whole object through the helper.
- **Every public page has its own title and description.** The homepage (the site name alone), the results, a home, the projects list and a project. A home or a project with no words of its own is described from its title, developer and place (`property.page.metaFallback`, `projects.page.metaFallback`). The results page follows the search: with no filter the plain title "Properties", with filters the heading ("Apartments for sale in Velachery") followed by the filters the heading does not already say (bedrooms, budget, keyword), so two searches never share a title. The comparison is `noindex` and so keeps the site description.
- **The canonical address of a search is its filters.** `canonicalSearchHref` writes them as the address contract does (alphabetical, defaults left out) and drops the sort, the number shown and the view, which change the layout of the same homes, not which homes they are. `?view=list` and `?sort=price_asc` share the filtered page's address. A home's canonical address is the one the page already redirects to (ADR-025).
- **The share image.** A home or a project shares its cover photo (described by the owner's words for it); every other page, and a home with no photo, shares a **default brand card drawn in code** at `/share-image.png` (1200 by 630: the arch mark, the name and the site's tagline, on the brand's dark green). The picture renderer cannot read CSS variables, so the four colours are written out in `src/styles/share-card.tsx`, the one place a colour may be written out, and a test fails if one drifts from its primitive in `tokens.css`. The address ends in `.png` so the proxy leaves it alone, and it is not under a path `robots.txt` shuts, so the crawlers that fetch share images may read it.
- **`robots.txt`** (`src/app/robots.ts`). In production it allows the site and shuts `/admin`, `/builder`, `/dashboard`, `/post-property`, `/auth`, `/reset-password`, `/compare`, `/api` and `/design-system`, and names the sitemap. In any other environment it shuts every path and names no sitemap (the proxy also sends `X-Robots-Tag: noindex, nofollow` there, as before). It waits for the request (`connection()`), so the environment is read when a crawler asks and not when the site was built: a build made for one environment can never answer for another.
- **The proxy leaves `/robots.txt` and `/sitemap.xml` alone** (the matcher in `src/proxy.ts`). They have no language prefix, so the language rewrite sent them to `/en/robots.txt`, which does not exist: crawlers got the not-found page. A test reads the matcher.
- **`noindex`** was already in place for sign-in, password reset, the account pages, the portals and the quiet administrator sign-in (their page groups), and for every non-production environment (the proxy header). `/compare` gains it here (`NO_INDEX`).
- **`sitemap.xml`** (`src/app/sitemap.ts`, `src/features/sitemap`). The built public pages (`/`, `/properties`, `/projects`; the contact and legal pages join when they are built), then every live project of an active builder and every approved home, each with the date it last changed (`updated_at`, a granted column). One file, at most **45,000 addresses** (the limit is 50,000; a site that grows past it splits the sitemap with `generateSitemaps`): projects first (at most 5,000), homes with what is left, newest change first; a log line says when the cap cut the list. The reads are as an anonymous visitor, so the database's own rules decide what exists, with only the granted columns; they page 1,000 rows at a time (PostgREST's `max_rows`), cached for minutes under the homes tag and the projects tag, so an approval refreshes them. **A read that fails, or a row that does not fit, throws and the sitemap answers 500**, so a crawler comes back later instead of trusting a partial list. It waits for the request (`connection()`), so a build with no database never bakes in an empty or failed list.
- **Structured data (JSON-LD)** on the property and project pages, next to the feature that owns the data. A home is a `RealEstateListing` with its price in rupees (per month for a rent, as a `UnitPriceSpecification`), the day it was published, its photos and what it is (`Apartment`, `House`, or a plain `Place` for a plot or commercial property): bedrooms, bathrooms, size in square feet, amenities and the place. A project is an `ApartmentComplex` with its name, up to six photos, number of units, amenities and locality. Both get a `BreadcrumbList` (Home, the list, the page itself). **No street address and no exact location, ever** (BR-90, BR-94): the place is the locality, city and state, and a test fails if a street, a coordinate, an owner or a contact number appears. Empty values are left out, never written as empty. `PropertyData` gains `publishedAt` (a column the page already read) for `datePosted`.
- **How it is written into the page.** `<JsonLd>` writes one `application/ld+json` data block as the text of a script tag, not as raw HTML (R-FE-14 forbids `dangerouslySetInnerHTML`): `serializeJsonLd` writes `<`, `>` and `&` and the two line separators as unicode escapes, so a title that holds `</script>` can never close the block, and the text still reads back as the same JSON. A data block is never executed, so the content security policy is unaffected.

## What is not done here

- **No language alternates** (`hreflang`): there is one language (DEC-40); a later language adds them.
- **No search-console verification, image sitemap, or Organization and site-search structured data**: not in the acceptance criteria.
- **No real-world validation of the structured data.** The tests check its shape; Google's Rich Results test needs a public address, so the owner runs it once before launch on a real home and a real project. **A project in the data is always an `ApartmentComplex`**: the project type column is not read by the page, so a plotted layout or a villa project still says so (a later change can pick the type from the column).
- **Not tried against real rows:** the hosted dev database needs secrets, so the sitemap's reads are tested with a stand-in and the pages' data in unit tests; the head tags, `robots.txt` and the share image were checked on a production build, and `sitemap.xml` was seen to answer 500 with no database.
- **The Design Lab and its pictures do not change**: nothing here is visible on a page.

## For the owner

- In the **production** environment `NEXT_PUBLIC_SITE_URL` must be the real domain: every canonical link, share address and sitemap entry is made from it (`docs/runbooks/environment-variables.md`).
- After launch: submit `sitemap.xml` in the search consoles you use, and run Google's Rich Results test on one home and one project.

## Words (new, for the owner's approval)

`results.meta.titleFiltered` ("{heading}, {filters}"), `results.meta.description` ("{title}. Photos, prices and details of homes on Find Prop."), `projects.list.metaDescription` ("Browse new projects with prices, sizes and possession dates on Find Prop."), `property.page.metaFallback` ("{title}. See the photos, price and details on Find Prop.") and `projects.page.metaFallback` ("{name} by {developer} in {locality}. See prices, plans and amenities on Find Prop."). The share image reuses the site's name and description (`meta.title`, `meta.description`), and the breadcrumbs reuse the pages' own crumb words.
