# ADR-115 · Sponsor management: the manager on the Hero page (S7-T11, part C)

- Status: Accepted
- Date: 2026-11-10
- Related: ADR-105 (the server side), ADR-106 (the picture slot and form), ADR-109 (the list, the preview and the layout notes), ADR-102 (the Hero page), FR-ADM-11, DEC-15
- Plan approved by the owner on 10 Nov 2026 ("approved") as two changes: C1, the logic that has no screen (this ADR's decisions), and C2, the connected Hero page (its wording is added to this ADR there). The owner's decisions of 9 Nov 2026 stand: every sponsor is eligible for the hero and for results, the advertiser's name is kept for staff only, there is no "Booking" line, the server removes the files of deleted or replaced pictures, there is no approval step, and scheduling, billing, reports and click counts are not built.

## Decision (C1: the logic, no screen)

- **One list of drafts, in the browser.** The Hero page keeps the sponsors as a list of drafts (`sponsor-draft.ts`): the stored sponsors as the server read them (`getSponsorsPage`), changed by Add, Edit, Delete, Move and Active. Each change gives a new list and is then sent as the whole list in its order, which is what `saveSponsors` takes. The rules are plain functions with tests: at most 10 sponsors (a full list cannot be added to), Move swaps with the neighbour and stops at either end, and the status is "Needs images" until a format has both pictures.
- **The browser checks what the server checks, and the server still decides.** `checkPicture` (`sponsor-upload.ts`) reads the start of the chosen file and applies the server's own rules (`slotProblem`): a PNG, JPEG or WebP by its own first bytes (a name or declared type proves nothing), no more than 150 KB, at least twice the slot's size, and a shape the slot can take (a near miss is accepted and shown whole). The person is told at once, in the slot, before anything is sent. `draftProblems` finds the box problems (a name, an alt text, an https link with no user name or password) and a format that has only one of its two pictures, with the same `validation.*` keys the server uses.
- **A picture is sent when the sponsor is saved, not when the file is chosen.** A chosen picture is held as the file itself, with a preview address the browser made. Pressing "Save sponsor" puts each new file in the public bucket `site-assets` under `sponsors/<the sponsor's id>/<random name>.<ending>` with the signed-in admin's own session (`sponsor-storage.ts`; the bucket's policies allow only the super admin to write), and then calls `saveSponsors` with the paths. A drawer that is cancelled therefore leaves nothing in the bucket. If a file cannot be sent, or the save comes back refused, the files sent in that attempt are taken away again and the drawer stays open with the problem on the box or slot it belongs to. The server reads every new file back and checks it again, and removes the files no sponsor uses any more after the list is written (ADR-105).
- **The hero picture and the layout notes use the public site's own rules.** `heroViewOf` turns the drafts into the same `SponsorAd` shape the home page reads and asks `heroCoverage` (ADR-109), so the preview shows the banner visitors would get and `layoutWarningOf` says whether no sponsor, or some sponsors, cannot show in the chosen layout. The page puts these into the notes with ICU plural words.
- **Sponsor changes save at once; the Hero text and layout keep their Save changes bar.** They are two different settings (`sponsors` and `hero`), saved by two different actions, so one can never overwrite the other. (C2.)

## Decision (C2: the connected Hero page)

- **Where it sits.** The Hero page (`/admin/hero`) keeps its text and layout boxes and their Save changes bar, and gains the Sponsors section under them (the `after` slot of `SiteContentLayout`). The preview becomes the preview with the banner (`SponsorHeroPreview`), and the layout cards carry the layout note and the warnings (`layoutNote`). `getHeroPage` also reads the stored sponsors; the page's key still comes from the hero text only, so a sponsor change never wipes the words being typed.
- **Sponsor changes save at once, apart from the Hero text.** Add, Edit, Active, Delete and Move each send the whole list in its order to `saveSponsors` and answer with the toast "Sponsor saved"; the hero words and layout are a different setting, saved by `saveHero` and its own bar. Nothing is saved while another sponsor save is running (the buttons are off). A save the server refuses puts the problem on the box or picture it names and keeps the drawer open; a failure with no box to blame is a toast and the page is read again.
- **Add and Edit in the drawer** (`ManagerDrawer` with `SponsorFields` and four `SponsorImageSlot`s). The drawer's form sits inside the Hero page's own form in the component tree, so its submit is stopped before it can reach the Hero save. Picking a file checks it at once and shows the slot as filled, shown whole (a near miss) or refused with the reason; a refused file takes the slot's old picture away from the draft (the slot then shows what the draft holds). Cancel leaves nothing in the bucket.
- **Delete asks first** (`ConfirmDialog`), then saves the shorter list; the server removes the files no sponsor uses any more (ADR-105). A sponsor the server finds fault with during a move or a delete (for example one saved by hand before the editor, with no name) is opened in the drawer with the problem shown.
- **At most 10 sponsors.** Add sponsor is off at ten, and the line under the list says why. The server holds the same limit.
- **Traceability:** FR-ADM-11 now lists S7-T11, the screen `ADD-11` and the test `UT-sponsors-panel`.

## Wording to confirm

From the approved screen and used as written (see also ADR-106 and ADR-109): "Sponsors", "Add sponsor", "Edit sponsor", "Save sponsor", "Cancel", "Sponsor saved", "It appears on the homepage straight away.", the form's boxes and hints, "Banner images" and its lines, the four slot names and sizes, "Fills the slot", "Will be shown whole on a plain background", "Rejected: wrong shape", "Rejected: too small", "Rejected: {n} KB is too large", "Delete {name}?" with its line and "Delete sponsor", the preview words and the two layout notes. The line under the heading is "Shown in this order, one after another." (decision of 9 Nov 2026, replacing "There is no automatic rotation").

New words, for your confirmation (all under `admin.siteContent.sponsors` in `en.json`):

- **List:** "You can keep up to 10 sponsors. Delete one to add another." (added after the note when the list is full); the count "N sponsors · M active" uses a plural ("1 sponsor · 1 active").
- **Layout note:** "Live layout: Search Desk. Changes apply on the next page load after you save." (the approved screen shows the layout name in bold; messages hold no markup, so it is plain text here). The warnings count in a plural: "1 of 3 sponsors doesn't have the Split format" / "2 of 3 sponsors don't have the Split format", with "It won't be shown …" / "They won't be shown …" and "Add a Panel image to it / each in Sponsors below."
- **Slot lines the screen does not draw as such:** "Rejected: this file isn't accepted" with "Upload a JPG, PNG or WEBP instead. SVG files can contain scripts." (the screen's example names SVG; the browser cannot know the kind of file it was given); "Rejected: too large in pixels" with "This is {w} × {h}. The most allowed on a side is 6000 pixels."; the wrong-shape line "This image is much taller / wider than the slot (about {a} : 1, the slot is about {b} : 1). Supply one close to the slot's shape."; "This picture was not accepted" (a refusal the server pins to a picture); "The picture could not be sent" with "Check your connection and try again."; "This picture is needed" with "A format needs both its desktop and its phone picture. Add this one, or remove the other."
- **Preview caption:** "{name} · first of {n} active" (the screen's own, with the name filled in).

## Consequences

- No migration, package, gate, environment or server change. C1 added `sponsor-draft.ts`, `sponsor-upload.ts`, `sponsor-storage.ts` and one constant (`SPONSOR_IMAGE_BUCKET`, held equal to the public side's `SPONSOR_BUCKET` by a test, because browser code of a feature may not import another feature's index). C2 adds `sponsors-panel.client.tsx` and `sponsor-words.client.tsx`, connects `HeroForm` and the `/admin/hero` page, and adds the `admin.siteContent.sponsors` messages. The Design Lab, its boards and its pictures are unchanged (the parts were built and approved in B1 and B2).
- What an admin sees changes on `/admin/hero` only: the sponsors section, the preview with the banner, and the layout note. Visitors see a changed banner only after an admin saves a sponsor.
- Rollback: revert C2 (the page goes back to the text and layout boxes); C1 can then stay or be deleted with its tests and the constant.
