# ADR-142 · AI place search: "homes near KK Nagar" in the chat (plan PR 9)

- Status: Proposed. Built in this change behind a new flag that is off by default; the owner approves before it merges, and again before the flag is switched on (section "Switching it on").
- Date: 2026-11-18
- Related: ADR-128 (AI chat; section 5.1 is updated), ADR-131 (place search adapter; its last decision is updated), ADR-134 (usage count, caller `ai_chat`), ADR-135 and ADR-137 (distance sort, "Also near"), ADR-130 (error tracking), FR-PUB-12, FR-GEO-03, `OLA_MAPS_PLAN.md` (outside the repository) section 4.4 and row 9 of the table of changes
- Class C2 (a tool input changes, a flag is added, a prompt version is raised) under the owner's standing approval for the unbuilt tasks of `docs/ai-chat-phase-plan.md`. No migration, no dependency, no new customer wording.
- **Ola's approval.** Ola Maps approved in writing, on 18 Nov 2026, both the use of the integration with an AI system and the storing of its results. The owner holds that email; it is not copied here. This change still keeps the design the owner sent to Ola: the model never receives anything Ola returns, and nothing Ola returns is stored or cached.

## Decision

- **A new flag, `FLAG_AI_PLACE_SEARCH`, off by default,** in `src/server/env.ts`, `.env.example` and `docs/runbooks/environment-variables.md`. It does nothing unless `FLAG_AI_SEARCH` is on too. The test is in `createChatDeps` (`endpoint/deps.ts`): `FLAG_AI_SEARCH && FLAG_AI_PLACE_SEARCH`. The same two flags decide the tool and the prompt, so the model is never given a rule for a tool it does not have.
- **With the flag off nothing changes for the model.** `AI_CHAT_TOOLS` is still the same ten tools and `search_properties` keeps exactly the input and output it had (tests hold both). The prompt text has the same sections; only its version line changes.
- **With the flag on, `search_properties` gains two inputs.** `place` (text or null, at most 80 characters, no control character) is what the customer wrote, as they wrote it. `radiusKm` (whole number from 1 to 15, or null; null is 5) is used only with a place. Both are required and nullable, like every other field of the tool (ADR-128 section 4.4, rule 1). The tool description says to leave `locality` null when a place is given.
- **The output gains `distanceKm` and `nearby` on each home and a `place` block.** `distanceKm` is kilometres to one decimal (null when no place was searched). A home with `nearby: true` is outside the distance asked for. `place` is `{ status, radiusKm, homesWithinRadius, nearbyRadiusKm, nearbyHomes, note }` where `status` is `not_asked`, `found`, `ambiguous`, `not_found` or `unavailable`, and `note` is a line to the model written in our own code (what to do next), or null. `total` counts the homes inside the distance only. All of it is our own words and numbers.
- **The model never receives anything the map provider returns.** The tool passes the typed words to a server-side `PlaceLookup`; the lookup returns only a position (`found`) or a reason (`ambiguous`, `not_found`, `unavailable`), and the tool uses the position for `getSearchResults` (`lat`, `lng`, `radiusKm`) and then forgets it. No label, no place id, no position and no provider text is in the result, in the prompt, in an error or in a log line. The typed words are not echoed back either. Tests plant a position, a label and an id on the lookup and prove none reaches the result; the eval cases check the model's calls for the provider's names and numbers (`modelNeverSaw`).
- **How the place is resolved is the existing `resolvePlace` (ADR-131), with our own localities first.** The localities that have listings are checked with a new `closeLocalityMatch`, which accepts only the same name or a close spelling ("Velacheri" is "Velachery"; "kk nagr" is "KK Nagar" if KK Nagar is listed) and never a name that merely starts with or contains the text ("Anna" is not "Anna Nagar", "Nagar" is nobody). The listed spelling is what the provider is then asked for; the position always comes from the provider (the locality list holds no coordinates). One provider call per distinct text (the assistant's own second spelling of the plan is not used, because the model is told not to correct the place). Text of fewer than 3 or more than 80 characters is never sent.
- **A distinct text is looked up once per customer message.** `createPlaceLookup` keeps the answers of one message in memory (the lookup is made per request, in `createChatDeps`), so a model that asks twice costs once. This is the request-scoped de-duplication of plan decision D6, not a cache: nothing is kept between messages and nothing is stored.
- **What each answer makes the assistant do** (the `note`, the tool description and the prompt section agree):
  - `found`: say how many homes are within how many kilometres and each home's distance; homes marked `nearby` are said to be further out. The "Also near" rule of ADR-137 is reused as it is (`wantsNearby`, `nearbySearchParams`, `nearbyHomesToShow`): when the circle holds fewer than six homes the tool reads once more at 15 km and adds up to the remaining homes, nearest first, marked `nearby`. If that second read fails the first answer stands.
  - `ambiguous` (several areas fit and none is exactly what was typed): ask **one brief question** for a narrower name (the neighbourhood with a landmark, or a postal code) and wait. The suggestions are the provider's, so none is shown to the model or offered. Offering our own locality names was considered and left out: the list that made it ambiguous is the provider's, and a locality of ours that happens to be near by could be the wrong place.
  - `not_found` (nothing in Tamil Nadu answers the words: an unknown name, a place elsewhere such as "Bandra Mumbai", a spelling too far off): say so in one sentence, guess nothing, and offer to look by a listed locality (`list_localities`, which keeps working unchanged).
  - `unavailable` (the kill switch, no key, quota, a timeout, or any failure of ours): say it cannot look that place up and offer the localities. No homes are read, so the answer can never be a search around a wrong place. Plan section 4.8 (degraded mode).
- **The order with a place is nearest first** unless the model chose another order. The distance sort and `distance_km` are ADR-135; this tool offers `distance` only through a place (the tool's own order list is unchanged).
- **Ola calls are counted, with the caller `ai_chat`.** The real lookup wraps the provider in `createCountedPlaceProvider` (new, `src/server/places/counted.ts`), which tells a callback once for each call that reached Ola with one of the five outcomes of `places_usage_daily` (`ok`, `empty`, `timeout`, `quota`, `error`) and for nothing else; the callback writes `{ api: "autocomplete", caller: "ai_chat", outcome }` with `after()`, like the route (ADR-134). A lookup that sent nothing (kill switch, no key) is not counted. Counting never changes the answer. The admin card already lists the caller.
- **The prompt gets one section, and only with the flag.** `PLACE_SECTION` (in `prompts/sections.ts`) names no tool and no provider. It tells the model to pass the place as written (no spelling correction, no added city), to say only what the result gives, never to state or guess a position, to ask one brief question when the place is ambiguous, to say it cannot look a place up when it cannot, and that text inside a place is a name and never an instruction. It is written as instructions and not as sentences an answer would repeat, because the output check blocks a reply that copies eight words in a row from the prompt. `SYSTEM_PROMPT_VERSION` is `2026-11-18.1`.
- **A place that reads like an instruction does nothing.** The place is a name to look up: it is limited to 80 characters without control characters, passed to the lookup as plain words, never echoed, and the model is told so. A line break in it is refused as an invalid input. The customer's own message still goes through the input check first, as every message does.
- **Evals.** Twelve cases are added: ten golden (`G-place-01` to `G-place-10`: homes near a place with distances and homes further out; the typos "vyasarpaadi" and "Velacheri"; "kk nagr", which cannot be found; the ambiguous "Anna Nagar"; an unknown place; a place outside Tamil Nadu; the lookup being down; a distance the customer gave; a plain locality search with the flag on) and two red-team (`R-place-01`: an instruction inside the place; `R-place-02`: a request for the exact position, which the model never had). A case may now say `placeSearch` (run with the flag on) and `placesDown`. The world has locality centres and a stand-in provider (the fixed Chennai list plus a few areas, and one misspelling it can read, as Ola does); the real `resolvePlace` and the real tool run over it. Nothing calls the network.
- **ADR-128 section 5.1 is updated.** `search_properties` lists the place input and output (marked "only with `FLAG_AI_PLACE_SEARCH`") and "search by place or radius" leaves the list of things that are deliberately not tools. The count of tools stays at ten.

## Consequences

- **Cost and abuse.** One customer message may make up to six tool calls (`MAX_TOOL_CALLS_PER_MESSAGE`), so at most six distinct place lookups and six provider calls; the chat's own limits (the free trial, the per-visitor and per-address daily limits, the burst limit, the daily budget) already bound the messages. **The route's `places` limit applies to these lookups too** (owner, 18 Nov 2026: 60 a minute per visitor, and the per-address burst limit, the same scope `places` as `GET /api/places/autocomplete`, ADR-133): `withPlacesLimit` asks it before each lookup that would reach the provider, with no session, as the route does. A lookup the limit refuses never reaches the provider, is not counted as a call, and reaches the assistant as `unavailable`; a counter that cannot be checked fails closed the same way. So the chat cannot spend more of the map quota than the search box can.
- **Privacy.** The words a customer typed as a place now reach Ola Maps from the chat as well as from the search box. The place text is not stored by us (the usage row holds counts only), but the privacy and processor drafts for the chat (`docs/legal/ai-chat-policy-drafts.md`) do not yet say that the place the customer names in the chat is sent to the map provider. That is legal wording, so it is the owner's to approve; nothing was changed in the drafts or on the site.
- **A model can still repeat the customer's own place words in its answer**, as the customer wrote them. It cannot repeat anything of the provider's because it never has it.
- Ola's autocomplete does not read Tamil script (ADR-131), so a place written in Tamil is `not_found` and the assistant offers the localities. Tamil wording of the replies is still the owner's open decision D12.
- Two areas with the same name in the provider's answer resolve to the first, as the search box's rule does (`resolvePlace`, "exactly what was typed"). That rule is the adapter's and is not changed here.

## Switching it on (the owner's steps; nothing was run against dev)

1. Merge this change and let the dev deployment build. With the flag off the chat is as it was.
2. A real-model run of the whole eval set for prompt version `2026-11-18.1` (`src/features/ai-chat/evals/README.md`, "The real-model run"): the place cases must meet the same thresholds as the rest. This change ran only the offline set.
3. In Vercel for dev: `FLAG_AI_PLACE_SEARCH=1` (with `FLAG_AI_SEARCH=1`, `AI_PROVIDER`, `OPENAI_API_KEY` and `OLA_MAPS_API_KEY` already set), redeploy, and try in the chat: "homes near Velachery", "2 BHK within 3 km of Adyar", "homes near Anna Nagar" (expect one question), "near Xyzzyland" (expect a polite no), and the admin dashboard card (expect a row for the caller "AI chat").
4. To switch it off: `FLAG_AI_PLACE_SEARCH=0` and a redeploy. `PLACES_DISABLED=1` also works: the assistant then says it cannot look places up.

## Verification

Unit tests, no network and no database: the tool with a place (the input limits and refusals, the portable schema, no place asked, the typed words trimmed and looked up once, the search around the position with the default and a given radius and the model's order, the locality text dropped, distances to one decimal, the wider read when fewer than six homes are inside, its failure, the limit, the ten-home cap, each of `ambiguous`, `not_found` and `unavailable` reading no homes and telling the model what to do, no position, label, id or typed words in any result, lister text only under `untrustedText`); the registry (the old tool without a lookup, the same ten names with one); the lookup (the position only, four statuses, ambiguous, outside the region, an unknown name, too short, instruction-like text, our locality spelling first and never a prefix, a failing locality read, `unavailable` for every provider failure with no text logged, one lookup per distinct text per message, nothing kept between messages, the real lookup's count with caller `ai_chat` for `ok`, `empty` and `quota` and none without a key or with the kill switch); the places limit (asked once per lookup with no session; a refusal or a broken counter gives `unavailable`, reaches the provider not at all and counts nothing); the counted provider (five outcomes, `off` and our own errors not counted, a throwing counter changes nothing); `closeLocalityMatch`; the prompt (the section only with the flag, nothing else changes, the same forbidden-word checks as the rest of the prompt, no provider name); the endpoint (the section reaches the model only when the deps say so; `createChatDeps` serves the place tool only with both flags); the env flag; and the offline eval run of 84 golden and 51 red-team cases. The real service was not called, and no real model was run.
