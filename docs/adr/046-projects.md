# ADR-046 · Projects list and project page (S4-T09)

- Status: Accepted (data layer); the list and the page are added by the next changes
- Date: 2026-11-05
- Related: ADR-043 (the property page, whose pattern this follows), ADR-041 (the homepage's project reads), ADR-017 (public projections), `docs/ux/final-ux/screens/projects.html` and `project.html`, FR-PUB-08, FR-PUB-09, BR-42, BR-94
- Plan approved by the owner on 5 Nov 2026: step A (this data layer), step B (the list at `/projects`), step C (the read-only project page at `/projects/[slug]`). **Step D, the lead form and the events, is a separate task** that needs its own security plan, because it writes data (`submit_project_lead`, `track_project_event`, rate limits, the assigned form).
- The owner's answers: the price trend is drawn as plain SVG with a table view, no locality chips (they are marked "proposed" and DEC-29 says only if approved), no city on the cards and a heading that takes the region name from the site content, the list is read to 60 projects with no paging, no Shortlist button until Save exists, the units table shows the first 20 units, and a floor plan opens its picture full size in a new tab.

## Decision for step A: the data layer (`src/features/projects`)

- **The address** is `/projects/{slug}`. The slug is the project's own (`a-b-c`, lower case letters and digits, 2 to 80 characters, the database's own check) and the database does not let it change after moderation, so unlike a home there is no id in the address. `parseProjectSlug` reads capitals as lower case and gives null, which is "not found", for anything that is not a slug (a space, a slash, a bad escape). `canonicalProjectPath` gives the path to redirect to when the address given differs from the stored slug.
- **Two cached reads, as an anonymous visitor,** so the database's own rules decide what exists: only approved and published projects (BR-42) of active builders (`builders!inner`, BR-94), and only the granted columns. The moderation columns, the form link, the exact location and the street address are never asked for, and a test fails if they are.
  - `getProjects()`: the list, featured first and then newest, up to 60. A failed read is `{ status: "failed" }` after logging the code only; the cached read throws, so a failure is never cached and "Try again" asks the database again. A redirect or prerender signal is let through, not called a failure.
  - `getProject(slug)`: one project with its first 20 units (and the count of all of them), the count of available units, and the latest 12 months of the price trend. No project is `missing`, which covers one never listed, one in review, one not published and one whose builder is not active. Anything else throws and is never cached: a failed read must not look like a project that is gone, and a row that does not fit is a failure, not "not found". Errors are logged by their code only. A unit or a month that does not fit is skipped and counted.
- **Cache:** minutes, under the `projects` tag, so an approval or an edit refreshes it. The homepage's project read keeps its own tag (`home-projects`); the admin actions of Stage 8 will refresh both.
- **Pure rules, no words** (`view.ts`): the facts for "Project overview" in the UX order and only when given (price range, BHK sizes, status, possession date when it is a real day, land area, total units, available units counted from the units that are listed, the RERA number only for a project under RERA that has one), the RERA tag, the BHK sizes without repeats or 0, the price range lowest first, the units in the order of the table (by floor, then unit number read with its numbers as numbers, units with no floor last), the units footer ("Showing N of M"), the price trend oldest month first, and the videos a page may link to (https only, no sign-in details in the address, each once, at most five).
- **The card's data** (`toProjectCard`): the cover comes from the public project bucket, described by the project's name since the developer gives no description. A project has no city of its own, so the card is given none; the list step makes the card draw the locality alone.
- `PROJECT_BUCKET` moved to `src/lib/storage-url.ts` beside `publicStorageUrl`; the homepage still exports it.

## Consequences

- The list and the page add no query of their own.
- Not tried against real projects: the hosted dev database needs secrets, so the reads are tested with a stub client.

## Decision for step B: the list (`/projects`)

- **Composition:** `app/[locale]/(public)/projects/page.tsx` reads the list (`getProjects`) and the site content, makes a `ProjectCard` for each project and gives `ProjectsScreen` the cards. `ProjectsScreen` fetches nothing and holds no state, so the Design Lab draws every state with sample projects. The title of the page is "Projects".
- **The page asks for the request first (`connection()`), so a failure is never baked in.** Every read is cached for minutes, but a failed one is not cached. If the page were prerendered at build time with no answer from the database, the "could not load" state would be written into the page itself and served until it was rebuilt. Asking for the request keeps the page fresh on each visit (the reads underneath are still cached) and lets `loading.tsx` show the outline meanwhile. This is the choice the results and property pages already make by reading the address.
- **Screen** (as `projects.html`): breadcrumb Home > Projects (a "Home" back link below 1024 px), "New launches", the heading, the line "New developments from developers on Find Prop. Only approved and published projects are shown.", then the grid of cards: 1 across, 2 from 768 px and 3 from 1100 px (the homepage's card grid). **The heading comes from the site content, not from the UX's "Chennai":** "Projects in {region}" with the region name in the italic accent (as the UX draws it) when the site content has one, and "New projects" without. Nothing in `en.json` names a city.
- **States:** loading (the outline as skeleton lines and three loading cards, two below 1100 px), "New projects are coming soon" with its line and "Browse homes" (to `/properties`), and the failed load: an alert "We couldn't load projects" with Try again, which asks the server for the page again (`router.refresh()`; a failed read is not cached, so it asks the database again) and shows it is busy meanwhile. In the Design Lab the button does nothing.
- **Locality chips are not built.** The UX marks them "Proposed filter" and DEC-29 allows them only if approved. If they are approved later, the localities should come from the site content (`homepage.localities`), not a typed list.
- **Shared component touched:** `ProjectCard` draws the locality alone when the project has no city (before, it would have drawn "OMR Navalur, "). Cards that are given a city are unchanged.
- **Design Lab:** a new entry, "Projects page" (four projects with a region name, one project without a region name, coming soon, failed, loading), on the **Discovery** board. (A new board would have added a link to every board's header: at 390 px that link wraps onto a third line and moves every board's picture, so seven unrelated baselines would change.) The project page joins the same board in the next change.
- **Words** (new, for the owner's approval, in `en.json` under `projects.list`): "Projects" (page title and last crumb), "New launches", "New projects", "Projects in {region}", the line under the heading, "Projects" (the list's name for screen readers), "Loading projects", "New projects are coming soon", "No projects are live right now. In the meantime, browse homes that are available today.", "Browse homes", "We couldn't load projects", "Check your connection and try again." and "Try again".
- **A failed read takes about 7 seconds to show.** The database client retries a failed read (a GET) three times with waits of 1, 2 and 4 seconds before it gives up, so with the database down the page waits about 7 seconds behind its loading screen and then shows "We couldn't load projects". The same holds for every other read made this way (the results page's search is a POST and fails at once). It is left as the library's default, which also covers a brief blip; switching it off (`retry(false)`) is a decision for the owner. The smoke tests of `/projects` wait up to 20 seconds for it.
- **Not built:** the locality chips, paging (the list is read to 60), the project page (step C). Not tried against real projects: the hosted dev database needs secrets, so the page was exercised with no database behind it (the failed state) and with sample projects in the Design Lab.

## Decision for step C: the project page (`/projects/[slug]`), in two changes

The plan's step C is built in two changes, as the property page's was: first the details (this change), then the enquiry card and the phone bar. Both are read-only; the lead form and the events stay step D.

- **Composition:** `app/[locale]/(public)/projects/[slug]/page.tsx` parses the address (`parseProjectSlug`), reads the project (`getProject`), sends a slug written with capitals to the canonical address (308) and gives `ProjectScreen` the project and the addresses of its files in the public project bucket. `ProjectScreen` fetches nothing and holds no state, so the Design Lab draws every state with sample projects. The page title is the project's own SEO title or its name; the description is its SEO description or the first paragraph of its description, cut at a word (`projectMetaDescription`).
- **Screen** (as `project.html`): breadcrumb Home > Projects > the project (a back link to all projects below 1024 px), the developer's monogram and name, the title with the locality and RERA tags, the gallery (with the Featured badge), Call, WhatsApp and Brochure, Project overview, About this project, Amenities, Specifications, Units, Floor plans, the price trend, Location advantages with Nearby places, Videos, and the price card beside the details (stacked below them on a phone, as the UX has it). **Every section the developer left empty is left out whole**, and a fact not given is left out of the overview, never a blank or a zero.
- **Call, WhatsApp and Brochure are plain links for now** (no events are recorded until step D). Call is a `tel:` link; WhatsApp is offered only for a number written with its plus (international form), because WhatsApp needs the country code and a local number could reach the wrong person; a local number gets Call alone. The brochure and WhatsApp open in a new tab. **Shortlist is not built** (it waits for Save, S5-T01).
- **Specifications:** the text is shown as name and value pairs when every line reads "Name: value" (the UX's list), otherwise as paragraphs. Nothing typed is dropped, nothing is read as HTML.
- **Units:** the first 20 units in table order, the status as a word with a dot (`StatusBadge`, kind unit), a dash for a detail not given, and "Showing N of M units" (M from the database's count). On a phone the table scrolls sideways, the Unit column stays, and a soft fade at the edge says there is more. That fade is the compare page's, now a shared pattern (`ScrollFade`, `patterns/scroll-fade.client.tsx`); the compare page uses it from there.
- **Floor plans** open the picture full size in a new tab (the owner's answer); there is no viewer. The caption is "Floor plan N": the database keeps no caption for a plan.
- **Price trend:** a line with the area under it and the values and months as real text, so they stay readable on a phone (the line is the only drawing, with a non-scaling stroke). "View as table" lists every month and value, and the chart has a text alternative with the first and last month. With fewer than two months there is no trend, so no chart and no section. The scale is in round steps from just below the lowest value to just above the highest (`trendScale`).
- **Location and videos:** advantages and nearby places as tags; videos as links named "Video N", only https addresses with no sign-in details, at most five (`videoLinks`).
- **Not found:** an address that is not a slug, and a slug no approved and published project has (never listed, in review, unpublished, builder not active), give "Project not found" with the one next step "See all projects". As on the property page, the response has status 200 and `noindex` because the page streams under its loading screen; a true 404 would need the read to finish before anything is sent. Not changed without the owner.
- **Shared things touched:** `CompareScroller` became `ScrollFade` (a pattern, header and Lab entry, tests moved), the text helpers shared with the property page moved to `src/lib/text.ts`, and `lib/format.ts` gained acres and month formatting. The property page's behaviour does not change.
- **Design Lab:** the **Discovery** board gets "Project page" (everything given, little given, not found, loading).
- **Words** (new, for the owner's approval, in `en.json` under `projects.page`, and `format.acres`): the breadcrumb, "Loading project", the photo description "{name}: photo {number}", "RERA applicable · {number}" and "RERA applicable", Call, WhatsApp, Brochure, "Project overview" with its labels (Price range, Configuration, Status, Possession, Land area, Total units, Available units, RERA number) and "{sizes} BHK", "About this project", "Amenities", "Specifications", the units table (Units, Unit, Floor, BHK, Area, Facing, Price, Status, "Showing {shown} of {total} units", "Swipe sideways on small screens"), "Floor plans" and "Floor plan {number}", the trend ("Price per sq.ft, last {count} months", "As entered by the developer (₹ per sq.ft)", the chart's text alternative, "View as table", Month, "₹ per sq.ft", "Price per sq.ft by month"), "Location advantages", "Nearby places", "Videos", "Video {number}", "Price and contact", "Possession {date}", and "Project not found" with its line and "See all projects".
- **Not built:** the enquiry card and the phone bar (the next change), Shortlist, tracking of Call, WhatsApp and the brochure (step D), the canonical `<link>`, structured data and the sitemap. Not tried against real projects: the hosted dev database needs secrets, so the read is tested with a stub and the page was exercised with no database behind it (the not-found screen) and with sample projects in the Design Lab.

## Decision for step C2: the enquiry card and the phone bar

- **The enquiry card** (`ProjectLeadCard`, UX "Interested in this project?") sits under the price card beside the details (below the details on a phone, as the UX has it): **Enquire or Site visit**, name and phone (required), email (optional), the preferred date (a site visit only, required) and a message (optional, with the counter). **Anyone can use it, signed in or not**: unlike a home's enquiry, the UX has no sign-in gate for a project. It is the screen only, like the property page's card: it holds what was typed and hands the request type and the values over; **it sends nothing** (the lead action, its rate limit and the assigned form are step D), so the page switches Send off and says "Sending enquiries is not open yet." The card is built with every state the UX shows, drawn from props: Enquire, Site visit, fields marked as missing, "Please wait a little" (the hourly limit) and the thank-you note that replaces the form. Its anchor is `#enquiry`.
- **The phone bar** (`ProjectMobileBar`, UX: Call, WhatsApp and "Enquire about this project"), below 1024 px: Call and WhatsApp as round icon buttons (each only when the project's number allows it, as in the details) and one copper button that **leads to the card** (`#enquiry`) lower on the page; the UX does the same and has no sheet for a project. The page leaves room under its last section (`pb-24`) so the bar never hides content, and the site's bottom navigation is not drawn on this page (it is not in its list).
- **Lives in the feature, not in the shared components:** both are specific to a project, so they are not new shared components; the Design Lab shows them on the Discovery board's "Project page" entry (the card in five states, the bar with and without a number).
- **Words** (new, for the owner's approval, `projects.page.lead` and `projects.page.bar`): "Interested in this project?", "Request type", Enquire, "Site visit", "Your name", Phone, Email, "Preferred visit date", Message, "Tell the developer what you would like to know.", "Send enquiry", "Request a site visit", "Sending enquiries is not open yet.", "Please wait a little", "You can send a limited number of requests per hour. Try again soon.", "Thank you, we have your details", "The developer's team will contact you on the number you gave." and "Enquire about this project". The card reuses the property enquiry card's "(optional)", the email example and the message counter.
- **Not built:** sending (a lead, a site visit), the hourly limit, the events for Call and WhatsApp, and the assigned dynamic form: step D.

## Decision for step D1a: the lead and event backend (S4-T09, plan approved 6 Nov 2026)

Plan approved by the owner on 6 Nov 2026 with every recommended answer. Step D is built in two changes: **D1a** (this one: the database functions, the actions and their tests; nothing visible) and **D1b** (the enquiry card wired to them, the project page's view tracking, and the Design Lab states). The assigned dynamic form (BR-49) is **D2** and waits for S5-T05 (there is no form builder yet, so no assigned form exists); D1 always uses the built-in form.

- **Who may send a lead (owner decision, 6 Nov 2026).** Anyone may read the list and the pages, but **sending an enquiry or a site-visit request needs a signed-in visitor with a verified phone** (`defineAction` with `auth: "verified-phone"`, which also refuses on the server a request that skipped the card). This replaces the earlier reading of the UX file (ADR-046, step C2: "anyone can use it"). The signed-out card is a gate like the property page's (D1b).
- **The phone is the account's, never the form's.** The action reads it from the verified token (`verifiedPhoneDigits`, digits only, as `project_leads.phone` holds them), so a request cannot be sent for another number. The action takes no phone from the browser.
- **Two database functions, for the server only** (`supabase/migrations/20261106100000_project_lead_functions.sql`). `submit_project_lead` stores the lead; `track_project_event` records an event; both are `security definer` and **execute is granted to `service_role` alone**, so an anonymous or signed-in caller with the publishable key cannot call them directly (a test calls them as both and expects "permission denied"). The calls go through `features/projects/service.ts`, which is on the service-role allow-list already (docs/engineering/security.md 4.3). A helper `public_project_id(slug)` says whether a project is visible: approved, published and its builder active (BR-94); anything else is "not found", so a withdrawn project takes no lead and records no event.
- **`submit_project_lead`:** the kind is Enquire or Site visit (a brochure lead is not made here: brochure is out of phase one). A site visit needs a date from today (India time) to a year ahead; an enquiry keeps no date. The visitor is a 40-character one-way hash (BR-75), never an address. Empty email and message are stored as nothing. It returns the new id; the action answers only that the request was received. **The lead table has no user column and none is added**: the lead holds the verified phone.
- **`track_project_event`:** returns whether the event was recorded. A **view is recorded once per visitor per project per hour** (BR-71); the same visitor and project are serialised with an advisory lock, so three requests at once record one view (an integration test checks it). Other kinds of event (Call, WhatsApp, brochure, shortlist, compare) are accepted by the function but **the action takes only `view` today**: the owner left Call, WhatsApp and brochure out of phase one, and Shortlist waits for Save (S5-T01).
- **The rate limit is in the action, not the function.** `defineAction` counts it at step 4 with the existing scopes `project_lead` (5 per visitor per hour, BR-72) and `project_event` (30 per visitor per minute, BR-71), then the idempotency key (one per form, so a double click or a retry stores one lead). `docs/engineering/database.md` says the function applies the rate limit; counting in the action is the project's standard pipeline and avoids counting twice. That file is a protected path, so it is left as it is, and this note is the record.
- **Failures are closed errors.** A project nobody can see is `NOT_FOUND`; a refused visit date is the date field's own "choose a date from today to one year ahead" (`validation.visitDateRange`, new word); anything else the database raises is `INTERNAL`.
- **What is not here:** the card's sending (D1b), the page's view tracking (D1b), the assigned form and its uploads, the CRM, a notification to the developer and the developer's lead list (Stage 7 and 8), and every event but a view.
- **Not run locally:** Docker is not installed on the build machine, so the migration, the pgTAP tests (`project_lead_functions.test.sql`, 41 assertions) and the integration tests (`project-leads.test.ts`) run for the first time in CI. `src/types/database.types.ts` was updated by hand in the generator's format for the three new functions; CI's `gen-types --check` is the proof.

## Decision for step D1b: the card sends, the page counts a view (S4-T09, plan approved 6 Nov 2026)

The second half of step D: the enquiry card of step C2 is wired to the actions of D1a. Nothing about who may send changes (a phone sign-in, D1a).

- **Gate or form, by who is looking.** `ProjectEnquirySlot` reads the account's verified phone from the token (`verifiedPhoneDigits`: the token only, no role queries) inside its own Suspense boundary with the shared card skeleton, so the details and photos are never held back by the sign-in check. A visitor with no verified phone, or a token that cannot be read, sees the **gate** (the safe answer; an unreadable token is logged, a plain "no phone" is not). The gate reuses the property page's links (`enquiryLinks`: sign in with `gate=enquire` and a way back to this project, or create an account) and its wording ("Sign in to enquire", "Create an account").
- **The form asks no phone.** The account's phone is shown masked (`+91 98••• ••345`) and locked, with a line saying it is the number the visitor signed in with. What is sent never contains a phone: the server reads the account's own (D1a). This is the project card's answer to the "form re-asks the phone" note kept for the property enquiry card.
- **Connected card.** `ProjectLeadPanel` makes one idempotency key when the form opens, checks the form with the same schema the server uses (name, email, the visit date inside today to a year ahead) before the round trip, and draws what the action returns: the thank-you note; field messages; "Please wait a little" for the hourly limit; and one **"We couldn't send your request. Please try again."** alert for any other failure or a request that does not get through. A form that was not accepted stays as typed, and a retry reuses the key, so one lead is stored. The date field carries the same window (`min` and `max`), counted from the server's clock in India.
- **Views.** `ProjectViewTracker` calls `trackProjectEvent` once per project shown, from the browser after the page loads, so a crawler that only reads the HTML is not counted; it never shows an error. The database keeps one view per visitor per project per hour (D1a), so a reload counts once.
- **Design Lab.** The Discovery board's project entries show the gate (new), the form with the locked phone, Site visit with its date, the marked fields, "please wait", the new "try again" alert and the thank-you note; the full page is drawn signed out and the sparse one signed in.
- **Words** (new, for the owner's approval, `projects.page.lead`): "Sign in with your phone to send an enquiry or request a site visit.", "We couldn't send your request. Please try again." and "The number you signed in with."; the gate's "Sign in to enquire" and "Create an account" repeat words already approved on the property page. "Sending enquiries is not open yet." is removed.
- **Not tested end to end.** CI has no database behind the app, so no project page can be opened in the smoke tests; the gate, the form, the actions and the page's wiring are covered by unit tests and the Design Lab pictures, and the database side by the D1a pgTAP and integration tests.
- **Not built:** the assigned form (D2, S5-T05), Call, WhatsApp and brochure events, Shortlist on a project (waits for Save, S5-T01), and the developer's notification and lead list.
